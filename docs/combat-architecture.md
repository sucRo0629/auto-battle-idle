# Combat Architecture

この文書は、戦闘システム全体の上位構造を整理するための設計メモである。
クラス個別のスキル、数値、習得レベル、JSON スキーマは [spec/classes-and-skills.md](spec/classes-and-skills.md) を正本とし、ダメージ・回復・CD・状態効果の詳細は [spec/combat.md](spec/combat.md)、座標・Wave・接敵は [spec/battle-field.md](spec/battle-field.md) を正本とする。

ここで扱うのは「このゲームの戦闘とは何か」「各ロールは何を担当するのか」「なぜ現在のクラス構成になっているのか」という、戦闘システムの設計思想である。

---

## 1. 戦闘の目的

このゲームの戦闘は、パーティ編成がステージ進行へ変換される自動処理である。

勝敗条件は単純で、敵全滅が Victory、プレイヤー全滅が Defeat である。しかし設計上の焦点は「誰が最も高いダメージを出すか」ではなく、次の 3 つの条件を同時に成立させることにある。

- 敵 HP を削り切ること
- 戦場条件を有利に保つこと
- 味方が倒れ切る前に戦闘を継続すること

したがって、戦闘は単一の DPS レースではない。
本作の戦闘は、**Kill / Flow / Survival の 3 レイヤーが同時に進行する自動戦闘システム**として整理できる。

```text
Combat
├─ Kill Layer      敵 HP を削る
├─ Flow Layer      戦場条件を変える
└─ Survival Layer  味方の生存を成立させる
```

この 3 レイヤーは上下関係ではない。
Kill は勝利条件を直接進め、Flow は勝利条件の成立しやすさを変え、Survival は敗北条件への到達を遅らせる。

## 2. Combat Layer

### 2.1 Kill Layer

Kill Layer は、敵 HP を直接減少させるレイヤーである。
戦闘の最終的な勝利条件は敵全滅であるため、Kill は戦闘を前へ進める主エンジンになる。

ただし、本作の Kill は「火力が高い職」という意味だけではない。
既存設計では、Kill は **どの敵を、どのイベント構造で、どの耐性軸に対して処理するか** で分業されている。

```text
Kill Layer
├─ Physical Kill  処理対象と攻撃イベントを操作する
└─ Magic Kill     出力の安定性・適応性を操作する
```

### 2.2 Flow Layer

Flow Layer は、戦場そのもののルール・構造・時間軸を操作するレイヤーである。
Flow は支援火力ではなく、**戦闘がどのような条件で成立するか**を変える役割を持つ。

Flow の価値は、直接の与ダメージ量では測りにくい。
接敵位置、行動精度、DoT やヒットの時間密度、ダメージの流れ、単体/範囲の変換などを通じて、Kill と Survival の効率を間接的に変える。

```text
Flow Layer
├─ Position Flow          どこで戦うかを変える
├─ Field / Time Flow      局所条件と戦闘テンポを変える
└─ Damage Structure Flow  ダメージの流れと形を変える
```

### 2.3 Survival Layer

Survival Layer は、プレイヤー全滅という敗北条件への到達を遅らせ、戦闘継続を成立させるレイヤーである。

Survival は Defender だけでも Healer だけでも完結しない。
Defender は「誰が、どの形の攻撃を、どこで受けるか」を担当し、Healer は「受けた損失を、どの時間軸で継続可能な状態へ戻すか」を担当する。

```text
Survival Layer
├─ Defense Control    被害の受け口を作る
├─ Recovery Control   HP と継戦時間を戻す
└─ Stability Control  バリア・軽減・解除で崩壊を防ぐ
```

## 3. Kill Layer

### 3.1 Physical Kill

Physical Kill は、敵の処理対象と攻撃イベント構造を操作する。

物理 Kill / Flow クラスの本質は、近接か遠隔かではなく、**Attack / Hit / Skill Gauge の組み合わせで、どの敵をどう処理するか**にある。
近接・遠隔は配置と射程の違いとして現れるが、設計上の主軸は「処理対象」と「イベント密度」である。

現在の Kill 寄り物理職は次のように整理できる。

| 分類       | 主な担当 | 操作しているもの                      |
| ---------- | -------- | ------------------------------------- |
| 単体突破   | 剣術士   | 高 DEF 敵に対する安定処理             |
| 高速処理   | 双刃士   | 瀕死敵への Hit 密度とフィニッシュ速度 |
| 遠隔処理   | 弓術士   | 遠隔敵への攻撃回数・連射構造          |
| 高耐久処理 | 弩砲士   | 高 Max HP 敵や貫通ラインへの重撃      |

Physical Kill が扱うのは、単なる物理ダメージ量ではない。
高 DEF、瀕死、遠隔、高 Max HP という敵側の問題を、それぞれ別の処理クラスへ割り当てている。
これにより、物理 Kill / Flow クラスの差分は「DPS の大小」ではなく「どの敵構造に適合するか」になる。

### 3.2 Magic Kill

Magic Kill は、出力の安定性と適応性を操作する。

魔法職は `damageType: magic` によって REG 軸へ攻撃するが、設計上の本質は「物理と別計算の火力」だけではない。
キャスターは、戦闘の出力・流れ・意味を操作する職群として設計されており、Kill 内では次の 2 種が中心になる。

| 分類            | 主な担当 | 操作しているもの                       |
| --------------- | -------- | -------------------------------------- |
| Fixed Kill      | 魔術師   | 状況依存の少ない基準火力               |
| Structured Kill | 印術師   | 条件に応じた攻撃効果・対象構造の最適化 |

魔術師は、戦闘における火力の基準線である。
条件分岐や戦場再定義ではなく、安定した魔法ダメージを提供することで、編成全体の Kill 能力を測る基準になる。

印術師は、火力そのものを単純に増やすのではなく、**乾印 / 坤印の付与・手動起爆・自動起爆による拡散 / 収束**で戦況に適応する。
これは Flow ではなく Kill である。
なぜなら、戦場ルールそのものを変えるのではなく、敵 HP を削る処理の効率を印の配置と起爆で再構成しているからである。
印は味方への付与や支援 buff ではなく、敵への overlay として保持し、同属性攻撃の手動起爆でのみダメージ化する。

法陣師は魔法職だが、主所属は Magic Kill ではなく Flow Layer として扱うのが自然である。
理由は、法陣師が操作している対象が「魔法ダメージ量」ではなく、味方を含むダメージ流量・集中・分配・転送という戦場構造だからである。

## 4. Flow Layer

Flow Layer は、Kill と Survival の前提条件を変える。
既存設計では、Flow 職は「処理対象を持たない」または「直接撃破性能ではなく戦場操作を主目的とする」クラスとして現れている。

### 4.1 Position Flow

Position Flow は、「どこで戦闘が発生するか」を操作する。

現在の主担当は槍術士である。
槍術士は、敵・味方の優先ターゲットを処理する職ではなく、前線へのバフ/デバフ、近接範囲、戦線の押し引きによって接敵領域そのものへ干渉する。

この役割は、[spec/battle-field.md](spec/battle-field.md) の `battleX` 単一座標設計と相性がよい。
戦闘位置が射程・接近・ノックバック・描画の共通正本であるため、位置を変えることは単なる見た目ではなく、攻撃可能プール、被弾対象、敵ターゲット選定の意味を変える。

Position Flow の設計目的は、敵を倒すことではなく、Kill と Survival が働く場所を整えることである。

### 4.2 Field / Time Flow

Field / Time Flow は、局所的な戦場条件と戦闘テンポを操作する。

現在の主担当は狩猟士である。
狩猟士は、視界妨害・罠・範囲 DoT・DoT 残り時間圧縮によって、敵の行動精度と戦闘速度を崩す職として設計されている。

この分類は、既存の Field Flow を上位概念として拡張した整理である。
狩猟士が扱っているものは、単なる「範囲」ではなく、局所エリア内の行動可能性、命中精度、DoT の時間密度である。
そのため、Field Flow と Time Flow は分離した別職というより、現状では狩猟士がまとめて担当する **局所戦場 + 時間密度制御** と見るのが自然である。

Field / Time Flow の設計目的は、敵 HP を直接削ることではなく、敵の行動と戦闘テンポを崩して、Kill の機会と Survival の猶予を作ることである。

### 4.3 Damage Structure Flow

Damage Structure Flow は、ダメージの流れと形を操作する。

現在の主担当は法陣師である。
法陣師は、単体/範囲の変換、ダメージ流量の再配置、味方を含む損失圧縮を扱う。
これは ATK buff や DEF buff ではなく、ダメージがどこに集中し、どこへ分配され、どのように無駄なく働くかを再設計する役割である。

このため、法陣師はキャスターでありながら Kill ではなく Flow に分類される。
敵 HP を削るための出力職ではなく、敵味方を含む戦場全体のダメージ構造を扱うからである。

Damage Structure Flow は、Kill と Survival の境界に位置する。
敵側に対しては火力の無駄を消し、味方側に対しては被害の受け方を変える。
同じ「ダメージ流量」という対象を、攻撃にも防御にも使う点がこの職群の特徴である。

## 5. Survival Layer

Survival Layer は、味方を生存させるための単一ロールではない。
Defender と Healer が別々の時間軸を担当することで成立する。

### 5.1 Defender

Defender は、被害の受け口と戦線の安定を作る。

敵のデフォルト単体ターゲットは [spec/combat.md](spec/combat.md) §敵の単体ターゲット選定 — 生存 `defender` がいればその中の最近傍。Defender は単に HP と DEF が高いユニットではなく、敵の単体攻撃がどこへ向かうかを **ロールと配置** で設計するロールである。

ディフェンダー内部の 3 職は、防御を「硬さ」ではなく「防御対象の違い」で分解している。

| 分類     | 主な担当 | Survival 上の役割                      |
| -------- | -------- | -------------------------------------- |
| 前線構築 | 鉄衛士   | 単一路線を受け止め、物理ラインを作る   |
| 戦線安定 | 護法士   | 範囲・魔法を含む崩壊リスクを吸収する   |
| 攻撃防御 | 闘技士   | 被弾を起点に拘束・反撃・制圧へ変換する |

Defender は「ダメージを消す」だけではない。
誰が被害を受けるか、どこで敵を止めるか、被弾を制圧へ変換できるかを担当する。

Defender の仕事は、defender ロールで単体を引き受けることだけではない。Defender は「誰が攻撃されるか」に加えて、「誰が前線を保持するか」「前衛がどのように被害を分担するか」を設計する。

- Target intake: 敵の単体 default が defender 優先（[combat.md](spec/combat.md)）
- Frontline control: 誰が戦線を保持するか
- Damage intake design: 前衛内で被害を一点集中させるか、分担させるか（護法陣 DR aura 等）

Guardian は main tank として受け口を一点集中で保持する。Paladin は front 全体で被害を分担し、Fighter を sub-defender 化することで戦線を安定させる。Duelist は局所戦闘で被弾を counter / control へ変換し、常時受け切るのではなく「崩しながら受ける」Defender として扱う。

移動型アタッカーの背後侵入や一時的な前進は、Flow / Move に属する戦場操作であり、その瞬間に Survival 上の恒久的な被害入口へ変換しない。Assassin のような rear assault は、「前に出た」ことと「前線を保持している」ことを同義にしない設計が必要である。

### 5.2 Recovery / Stability / Sustain Control

Recovery / Stability / Sustain Control は、受けた損失を戦闘継続可能な状態へ戻す。

本作の Survival 主軸クラスは、Lv0 時点では火力貢献を抑え、回復・バリア・HoT・軽減・デバフ対策へ寄せられている。
これは、維持・安定化手段を Kill Layer の補助火力にせず、Survival Layer の正本として扱うための設計である。

現在の 3 職は、回復を単一の heal 量ではなく、損失への対応方法で分担している。

| 分類      | 主な担当 | Survival 上の役割                                                      |
| --------- | -------- | ---------------------------------------------------------------------- |
| Recovery  | 療養師   | 欠損 HP を戻し、余剰回復をバリアへ変換し、崩壊後の損失を即応で回収する |
| Stability | 結界師   | バリアとダメージ軽減で崩壊前に猶予を作る                               |
| Sustain   | 薬草師   | HoT、DEF buff、敵 `atk` debuff、debuff/DoT 対策で長期戦を支える        |

この 3 分類は、同じ「回復役」の数値違いではない。

- Recovery は **欠損後の復元**
- Stability は **崩壊前の猶予作成**
- Sustain は **被害の時間分布の平準化と長期維持**

を担当する。

療養師の上位個性は、継続維持ではなく **崩壊後の即応復元** に置く。大きな被害が発生した直後に即時 heal を返すことで、Recovery Control の最終形を担う。現行仕様では、まず `time` + `firePolicy: smart` + `fireConditions` による待機型即応 heal を許容する。

薬草師が持つ敵 debuff は、Flow のような戦場条件変更ではなく、**被害量・被害速度の抑制** として Survival 側に留める。命中妨害、位置操作、罠、DoT 時間密度操作など、戦闘成立条件そのものを変える効果は Flow 側の担当とする。

Recovery / Stability / Sustain Control は、Defense Control が作った受け口を維持する。
Defense Control が被害を集中・分散・制御し、Recovery / Stability / Sustain Control がその被害を時間の中で処理することで、Survival Layer が成立する。

### 5.3 Defense Control と Recovery / Stability Control の関係

Defense Control と Recovery / Stability Control の関係は、「前者が受け、後者が回復する」という単純な直列ではない。

Defense Control は被害の入口を設計する。
Recovery / Stability Control は被害の後処理と継続時間を設計する。

```text
敵の攻撃
  → Defense Control が受け口・位置・ターゲット優先・制圧で形を整える
  → Recovery / Stability Control が HP / barrier / HoT / dispel で継戦可能な状態へ戻す
  → Survival Layer が敗北条件への到達を遅らせる
```

この分業により、Survival は「耐久ステータスの合計」ではなくなる。
どの攻撃形態に強い Defender を置くか、どの損失処理に強い Healer を置くかで、同じ総回復量でも戦闘の安定性が変わる。

## 6. クラス群が操作しているもの

現在のクラス構成は、ロール名よりも「何を操作しているか」で見ると構造が明確になる。

| レイヤー | クラス群                          | 主に操作しているもの                       |
| -------- | --------------------------------- | ------------------------------------------ |
| Kill     | 剣術士 / 双刃士 / 弓術士 / 弩砲士 | 敵の処理対象、Hit 密度、攻撃回数、耐性適合 |
| Kill     | 魔術師 / 印術師                   | 魔法出力、攻撃効果の条件適応、対象構造     |
| Flow     | 槍術士                            | 接敵領域、前線圧力、位置による戦闘条件     |
| Flow     | 狩猟士                            | 局所エリア、行動精度、DoT 時間密度         |
| Flow     | 法陣師                            | ダメージ流量、集中/分配、単体/範囲構造     |
| Survival | 鉄衛士 / 護法士 / 闘技士          | 被害の受け口、戦線安定、被弾起点の制圧     |
| Survival | 療養師 / 結界師 / 薬草師          | HP 回復、バリア、HoT、軽減、状態異常対策   |

この整理では、`defender` / `attacker` / `supporter` という UI 上のロール分類と、Kill / Flow / Survival という戦闘構造分類を分けて扱う。
設計定義では UI ロール語ではなく、どの機能レイヤーへ影響するかを正本とする。

特に重要なのは、Flow が UI ロール内の変則枠ではなく、Combat 全体の第 2 レイヤーとして振る舞っている点である。
槍術士・狩猟士・法陣師は、いずれも敵 HP を削るだけでは説明できない。
これらは Kill の亜種ではなく、Kill と Survival の条件を再定義するクラス群である。

## 7. なぜこのクラス構成なのか

現在の 15 クラス構成は、UI 上の 3 ロールを数合わせで埋めるためのものではない。
設計から読み取れる意図は、戦闘を以下の問題へ分解し、それぞれに担当クラスを置くことである。

| 戦闘上の問題                   | 担当レイヤー | 設計上の解き方                           |
| ------------------------------ | ------------ | ---------------------------------------- |
| 敵を倒す必要がある             | Kill         | 敵タイプごとに処理方法を分ける           |
| 敵の配置・行動・時間密度が厄介 | Flow         | 戦場条件そのものを変える                 |
| 味方が倒れる                   | Survival     | 被害の入口と後処理を分業する             |
| 自動戦闘でも戦術差を出したい   | 全レイヤー   | 事前編成が戦闘条件へ反映されるようにする |

この構成の核心は、プレイヤーの操作ではなく**編成が戦術になる**ことにある。
戦闘中に細かく指示しない代わりに、どのレイヤーへ何枠を割くか、どの問題へ適合するクラスを入れるかが戦闘結果を左右する。

そのため、本作のクラスは「同じ目的を違う数値で実現する職」ではなく、**戦闘システムの別々の操作点を担当する職**として設計されている。

## 8. Combat Feedback

戦闘中は、数値、状態、イベントを分離して表示する。

本作はタイムアタックやダメージ量そのものではなく、解法が機能したこと、クラスが仕事をしたことを伝える。そのため、数値よりもイベント通知を優先する。

**フェーズ注記（v1）:** 本番 VFX PNG は未投入（[phase-roadmap.md](plans/phase-roadmap.md) Phase 5a–5c / 7）。その間は **popup と HUD** がスキル・パッシブ検証の主要手段。実装表・経路は [combat.md](spec/combat.md#combat-feedbackvfx-なしv1) を正とする。本番 VFX 投入後、Event Popup の一部は専用 VFX で省略しうる（Damage 数値 popup は別判断）。

### 8.1 HUD

HUD は継続状態を表示する。

例は次の通り。

- HP
- Barrier
- Buff
- Debuff
- Stack
- Status Effects

HUD 情報は原則としてポップアップしない。

### 8.2 Damage Popup

Damage Popup は、次を表示対象とする。

- Damage
- Heal
- DoT

ダメージ内訳は表示しない。

```text
OK

420

NG

120
+300 Armor Break
```

### 8.3 Event Popup

Event Popup は瞬間的なイベントのみ表示する（短いラベル。スキル名・ダメージ内訳は載せない）。

**v1 対象** — 実装: `CombatReactionPopupManager` / `BattleView` → `IBattleRenderer`

| 表示           | 主な発火                |
| -------------- | ----------------------- |
| 回避！         | `evade`                 |
| ブロック！     | `block`                 |
| 反撃！         | skill `effect: counter` |
| 無敵！         | `invulnerable`          |
| 再起！         | `lastStandRecovery`     |
| 不屈！         | `lastStandGuts`         |
| 引き寄せ！     | skill `enemyReelIn`     |
| ノックバック！ | knockback 系            |
| 肩代わり！     | `lowHpCover`（闘技士・攻撃誘導） |

**v1 対象外（Event ラベル不要）**

| 名称（旧例示） | 理由                                                          |
| -------------- | ------------------------------------------------------------- |
| Redirect!      | 余剰回復転送は heal 数値 popup のみ                           |
| Barrier Break! | バリア残量・付与は HUD（HP バー tier）。吸収量も popup 非表示 |
| Execute!       | 処刑・即死 effect 未実装。スキル追加まで不要                  |
| Armor Break!   | §8.2 の内訳 NG 例の illustrative 名称のみ。mechanic なし      |

### 8.4 表示位置

Damage Popup はキャラクター頭上に表示する。

Event Popup は Damage Popup より少し上に表示する。

キャラクター中央には表示しない。理由は次の通り。

- キャラクターが隠れる
- スキル演出が見えなくなる

### 8.5 Barrier

Barrier 吸収量は表示しない。

Barrier 残量は HUD で確認する。

### 8.6 Redirect

Redirect 量は表示しない。

- `excessHealRedirect` — 転送先に heal 数値 popup
- `lowHpCover`（攻撃誘導）— 闘技士頭上に **肩代わり！** Event Popup

### 8.7 設計思想

本作で伝えるべきものは、ダメージ量ではなく、解法が機能したこととクラスが仕事をしたことである。

そのため、数値よりもイベント通知を優先する。

## 9. 設計哲学

### 9.1 確定結果レイヤー

戦闘結果レイヤーでは、ダメージ・回復量・状態変化・生存状態を必ず確定値として扱う。
回避、ブロック、防御無視、デバフ付与、確率反撃などの確率要素は、判定時にのみ使用できる内部処理であり、戦闘状態として「成功するかもしれない」「失敗するかもしれない」という中間状態を保持しない。

```text
未判定状態
  → 判定（chance 等の内部処理）
  → 確定状態（成功 / 失敗、適用 / 非適用、発動 / 非発動）
```

この意味で、本作の「完全決定性」は「確率パラメータを一切持たない」ことではなく、**戦闘ログ・BattleSnapshot・HP・StatusEffect・生死判定に出る結果がすべて確定済みである**ことを指す。
戦闘の基礎計算には最終ダメージ・回復量の乱数ブレを置かず、確率判定を含む処理も判定直後に確定結果へ収束させる。

これにより、勝敗や安定性は未解決の確率状態ではなく、編成・射程・ターゲット・CD・状態効果・判定済みイベントの結果として読める。

### 9.2 戦闘ルールと描画の分離

戦闘位置の正本は `battleX` であり、描画はそれを参照する。
`src/render` は戦闘ルールを持たない。
この分離により、Flow が扱う位置・接敵・ノックバックは見た目の演出ではなく、実際の戦闘条件として意味を持つ。

### 9.3 支援を火力に還元しすぎない

既存設計では、Survival 主軸スキルの Lv0 火力 buff / 敵被ダメ debuff は制限されている。
これは、すべての維持・安定化手段を DPS 増加へ寄せると、Kill / Flow / Survival の分離が壊れるためである。

支援は「火力を上げる」だけでなく、被害の受け方、戦線の安定、状態異常対策、行動テンポの変化として表現される。

### 9.4 Flow は支援ではなく戦場操作

Flow 職は、Kill 職の補助枠ではない。
Flow は、敵を倒す処理そのものではなく、敵を倒せる条件・倒されない条件を変更する。

このため、Flow の評価軸はダメージメーターではなく、接敵位置、攻撃可能プール、敵行動精度、DoT 時間密度、ダメージ流量、損失圧縮などになる。

### 9.5 防御は硬さではなく対象設計

Defender は「耐える量」だけで分かれない。
鉄衛士は単一路線、護法士は戦線全体、闘技士は被弾起点の制圧を担当する。
防御対象を分けることで、ステージ構造や敵構成に応じた編成選択が生まれる。

### 9.6 自動戦闘における戦術

このゲームの戦術は、リアルタイム操作ではなく事前設計で表現される。
クラス、射程、defender 優先ターゲット、ターゲット条件、CD、状態効果、Wave 構造が、戦闘中に自動で解決される。

したがって、戦闘設計の目的は「操作がないのに結果が変わる」ことではなく、**操作しないからこそ編成意図が戦闘構造へ反映される**ことである。

## 10. 今後の設計判断に使う基準

新クラスや新スキルを追加するときは、まず次のどの操作点を担当するかを決める。

```text
1. 敵 HP を削るのか          → Kill
2. 戦場条件を変えるのか      → Flow
3. 味方生存を成立させるのか  → Survival
```

そのうえで、既存クラスとの差分を「数値」ではなく「操作対象」で説明できるかを確認する。

- Kill なら、どの敵構造・耐性軸・イベント構造を処理するのか
- Flow なら、位置・時間・行動精度・ダメージ流量のどれを変えるのか
- Survival なら、被害の入口・回復・バリア・軽減・解除のどこを担当するのか

この基準で説明できないクラスは、既存クラスの数値違いになりやすい。
逆に、この基準で説明できるクラスは、既存構造と矛盾せずに拡張できる。
