# ローグライクモード（仮称）

メインステージ攻略後も継続して遊べる、**ランダム問題を解く**モードの設計仕様。

**関連:** [progression.md](progression.md)（メインモード進行）、[combat.md](combat.md)（戦闘ルール）、[classes-and-skills.md](classes-and-skills.md)（クラス・スキル）、[../combat-architecture.md](../combat-architecture.md)（Kill / Flow / Survival）

**用語（本モード）**

| 用語 | 意味 |
| ---- | ---- |
| **ラン** | ローグライクモードの 1 プレイ単位。開始から敗北またはクリアまで |
| **問題** | 1 ノードまたは 1 戦闘で提示される敵構成・補正・制約の組 |
| **世界補正** | ラン開始時に付与され、ラン全体に効く環境ルール |
| **制約** | プレイヤーに不利な条件。代わりに報酬を増加させる |
| **報酬** | ノードクリア後に選択する強化。数値上乗せより挙動変化を優先する |

**モード名:** 仮称。本番名称は未確定。

---

## 1. 目的

メインステージ攻略後も継続して遊べるモードを提供する。

目的は育成周回ではなく、次を無限に供給すること。

- **編成実験** — 固定メタから外れた組み合わせの検証
- **クラス研究** — 普段使わないクラス・ルール変化の体験
- **解法探索** — 提示された問題に対する最適解の発見

---

## 2. 設計思想

### 2.1 本プロジェクトにおける位置づけ

一般的な放置ゲームの

```text
育成 → 数値上昇 → 次ステージ
```

ではなく、

```text
問題発生 → 解法発見 → クリア
```

を繰り返す設計を採用する（[combat-architecture.md](../combat-architecture.md) の Kill / Flow / Survival 構造と整合）。

ローグライクモードは、**固定問題を解くメインモード**に対する、**ランダム問題を解くモード**として位置付ける。

### 2.2 成長の優先順位

一般的なローグライクの

- 攻撃力 +10%
- HP +20%
- クリティカル率 +5%

のような **数値成長中心** にはしない。

優先するのは次の変化である。

| 優先 | 内容 |
| ---- | ---- |
| 高 | 問題変化（敵構成・性能傾向） |
| 高 | 環境変化（ステージ補正・世界補正） |
| 高 | 制約変化（編成・能力の制限） |
| 高 | クラスルール変化（スキル挙動の変更） |
| 低 | 汎用ステータス上乗せ |

数値報酬も存在しうるが、**解法そのものを変える報酬** を設計上優先する。

---

## 3. メインモードとの役割分担

| | メインモード | ローグライクモード（本 spec） |
| --- | --- | --- |
| 問題 | 開発者が用意した固定ステージ（`stages.json`） | ランごとに生成されるランダム問題 |
| 体験 | 意図された解法体験の提供 | プレイヤー自身による解法発見 |
| 進行 | セーブ永続・個別 Lv・ステージ進行（[progression.md](progression.md)） | ラン内一時状態。ラン終了でリセット |
| 育成目的 | ステージ攻略・キャラ Lv 成長 | **非目的**（後述のエンドレスも同様） |
| 戦闘 | 既存 `BattleEngine` による完全自動戦闘 | 同一戦闘基盤を利用（ルール差分はデータ・モディファイアで与える） |

メインモードのセーブ・EXP・`globalExp`（Phase 9）とは **独立したラン状態** を持つ。ラン外への永続育成への転用は本 spec では定義しない。

---

## 4. 基本ループ

```text
開始
  ↓
問題生成（マップ / 初戦）
  ↓
編成
  ↓
自動戦闘
  ↓
報酬選択（勝利時）
  ↓
進路選択（マップ上）
  ↓
次の問題 …
  ↓
ボスクリア or 敗北 → ラン終了
  ↓
（エンドレス継続時）次の問題へ …
```

戦闘中のプレイヤー操作は行わない（メインモードと同様の完全自動戦闘）。

---

## 5. プレイヤー操作

プレイヤーが行う操作は次のみ。

| 操作 | タイミング | 内容 |
| ---- | ---------- | ---- |
| **編成** | 戦闘前 | パーティメンバー・配置の決定 |
| **報酬選択** | ノードクリア後 | 提示された報酬から 1 つ（または規定数）を選択 |
| **進路選択** | マップ上 | 次に進むノードの選択 |

上記以外（戦闘中のスキル発動・ターゲット指定等）は行わない。

---

## 6. ステージ生成（問題生成）

敵をクラス体系で編成し、問題として提示する上位方針は [enemy-design-concept.md](../enemy-design-concept.md) を参照。

各戦闘ノードは、次のパラメータ組み合わせで **問題** として生成する。具体の重み付け・シード・データ形式は実装フェーズで定義する。

### 6.1 敵構成パターン

| パターン | 概要 |
| -------- | ---- |
| 雑魚ラッシュ | 低個体・高数のウェーブ |
| エリート混成 | 通常敵 + 強化個体の混在 |
| 単体ボス | 1 体の高脅威 |
| 複数ボス | 複数の高脅威同時 |

既存 `enemies.json` のテンプレートをベースに、ラン用の生成ルールで組み立てる想定。

### 6.2 敵性能傾向

生成時に 1 つ以上の傾向タグを付与し、敵ステまたは AI 優先度を偏らせる。

| 傾向 | 解法への示唆（例） |
| ---- | ------------------ |
| 高 HP | 持続ダメージ・削り |
| 高攻撃 | 生存・被害抑制 |
| 高防御 | 防御無視・ DoT |
| 高速攻撃 | 行動制限・早期撃破 |
| 範囲攻撃 | 分散・後列保護 |
| 後列狙い | 前衛・ Conductor 系の配置 |

### 6.3 ステージ補正

戦闘フィールドまたは Wave 単位で適用する環境ルール。

| 補正例 | 効果の方向性 |
| ------ | ------------ |
| DoT 有利 | DoT ダメージ・持続の強化 |
| 多段攻撃有利 | ヒット数依存効果の強化 |
| 回復量変化 | 回復スキル・ REG の増減 |
| 被ダメージ変化 | 全体または条件付きの `damageTaken` 補正 |

補正は [combat.md](combat.md) の既存 effect / パッシブ機構、またはラン専用モディファイアとして実装する。

## 7. マップ構造

一般的なローグライクの分岐マップ構造を採用可能。

### 7.1 ノード種別（例）

| 種別 | 役割 |
| ---- | ---- |
| 通常戦闘 | 標準的な問題。基本報酬 |
| エリート戦 | 高難度・高報酬 |
| イベント | 非戦闘または特殊ルール（具体内容は未確定） |
| 商店 | 報酬・編成変更の交換（具体ルールは未確定） |
| 休憩 | 回復・準備（具体効果は未確定） |
| ボス | ラン区切りまたはクリア条件 |

### 7.2 進路

- 各層（または区画）で複数ノードが分岐し、プレイヤーが **進路選択** する。
- 到達可能ノード数・ボス前の層数は未確定（実装フェーズでデータ化）。

---

## 8. 報酬設計

### 8.1 方針

数値強化よりも、**解法そのものを変える報酬** を優先する。

| 優先度 | 報酬の種類 | 例 |
| ------ | ---------- | -- |
| 高 | クラスルール変化 | 後述 §9 |
| 高 | 世界補正の追加・強化 | 特定 Kill / Flow 軸の強化 |
| 中 | 制約解除・緩和 | 職制限の一部解除 |
| 低 | 汎用ステ上乗せ | ATK / HP 百分率 |

### 8.2 提示タイミング

- 戦闘ノードクリア後、**報酬選択** UI で複数候補から選択。
- エリート・ボス・制約付き問題では候補数または品質を増加させる（具体数値は未確定）。

### 8.3 メインモードとの関係

- ラン内報酬は **ラン終了で失効** する（エンドレス継続中もラン内状態として保持）。
- メインモードの `playerProgress`・`build`（習得スキル）・Phase 9 の globalExp 強化には **直接反映しない**。

---

## 9. クラスルール変化

報酬および世界補正の主要カテゴリ。数値より **挙動変化** を優先する。

既存クラスの `classId` は [classes-and-skills.md](classes-and-skills.md) に従う。以下は設計上の代表例（全クラスに同様の方針で拡張可能）。

### 9.1 魔術師（`at_sorcerer`）— MultiLock 軸

| 変化例 | 内容 |
| ------ | ---- |
| Lock 対象数増加 | multiLock の同時ロック数拡張 |
| 単体時 Lock 挙動変更 | 敵が 1 体のときの再配分・集中ルール変更 |
| Lock 優先対象変更 | ターゲット選定（nearest / 低 HP 等）の上書き |

### 9.2 印術師（`at_sigilist`）— 印起爆軸

| 変化例 | 内容 |
| ------ | ---- |
| 印 stack 上限増加 | 乾印 / 坤印（`windMark` / `earthMark`）の同時保持上限 |
| 印持続変更 | 乾印 / 坤印の持続時間・自動起爆タイミング |
| 手動起爆補助 | 共鳴ボーナス・重ね鳴り・早鳴り系の係数拡張 |

### 9.3 法陣師（`at_conductor`）— Flow / damage routing 軸

| 変化例 | 内容 |
| ------ | ---- |
| 回収対象拡張 | reservoir へ記録する damage 源の拡大 |
| 集中対象変更 | Convergence Field の収束先ルール |
| 分散対象変更 | Distribution Field の分配先・比率 |

### 9.4 その他クラス

Hunter / Defender / Healer 等も、既存の Kill / Flow / Survival 機構に沿った **ルール変化** として定義する。汎用 ATK+% のみの報酬は避ける。

---

## 10. 世界補正

**ラン開始時** に 1 つ以上付与され、ラン全体（または規定ノード）に効く環境ルール。

毎回異なる最適解を発生させるための **解法誘導**（§12）とも連動する。

| 名称（例） | 概要 | 主に強化する軸 |
| ---------- | ---- | -------------- |
| 潮流異常 | Conductor 関連 effect の強化 | Flow（damage routing） |
| 魔力暴走 | Sorcerer 関連 effect の強化 | Kill（multiLock 純出力） |
| 印共鳴 | Sigilist 関連 effect の強化 | Kill（印起爆・手動起爆最適化） |

名称・効果量・スタック可否はデータ化時に確定する。上記 3 つに限定しない。

---

## 11. 制約システム

プレイヤーに **不利な条件** を課す代わりに、当該問題またはランの **報酬を増加** させる。

### 11.1 職制限

| 制約例 | 効果 |
| ------ | ---- |
| 特定クラス使用不可 | 例: `at_sorcerer` 禁止 |
| ロール制限 | 例: Healer 系クラス禁止（具体 classId 集合はデータ化時） |

### 11.2 編成制限

| 制約例 | 効果 |
| ------ | ---- |
| 前衛上限減少 | 前衛スロット数の減少 |
| 後衛上限減少 | 後衛スロット数の減少 |
| パーティ人数上限 | 4 未満での出撃（未確定） |

編成スロット定義は [battle-field.md](battle-field.md) の隊形と整合させる。

### 11.3 能力制限

| 制約例 | 効果 |
| ------ | ---- |
| 回復量減少 | 回復 effect の倍率低下 |
| 最大 HP 減少 | 味方 `maxHp` のラン内減算 |

制約は問題（ノード）単位またはラン全体単位のいずれかで付与可能（適用スコープは未確定）。

---

## 12. 解法誘導システム

### 12.1 目的

**毎回同じ編成・同じ解法が最適になる** ことを防ぐ。

ランごとに世界補正・敵傾向・制約・報酬プールが変わることで、最適解を変化させる。

### 12.2 誘導の手段

| 手段 | 強化側の例 | 弱体側の例 |
| ---- | ---------- | ---------- |
| 世界補正 | Hunter 強化、Defender 強化、DoT 強化 | MultiLock 弱体、回復量低下 |
| 敵性能傾向 | 後列狙い → 前衛・ Flow 必須 | 高防御 → 防御無視軸 |
| 制約 | — | 特定クラス禁止 → 代替解法 |
| 報酬プール | 採用クラス向けルール変化を多めに提示 | 汎用ステのみの候補を減らす |

「強化」と「弱体」は **同ラン内でセット** として設計し、単一軸の永久強化にならないようにする。

## 13. クラス利用方針

### 13.1 全クラス使用可能

基本方針として、**プレイヤーがメインモードで解放済みの全クラス** をランで使用可能とする。

面白さの中心は

```text
「どのクラスを引くか」（ガチャ）
```

ではなく

```text
「どのクラスを使うか」（編成判断）
```

とする。

### 13.2 解放条件

メインモード側のクラス解放ルールが存在する場合、それに従う。現行 Phase 2 では全クラスが最初から使用可能なため、**セーブ上解放済み classId の集合** を正とする。将来の解放システム追加時は本節を更新する。

### 13.3 レベル・ビルド

ラン内で参照する Lv・習得スキルは、次のいずれかで定義する（**未確定**。実装フェーズで選択）。

| 案 | 概要 |
| -- | ---- |
| A. メイン同期 | セーブの `playerProgress` + `build` をそのまま使用 |
| B. ラン固定 | 全員同一 Lv（例: Lv20 相当）で習得枠最大 |
| C. ラン内成長 | ラン専用 Lv（メインに反映しない） |

## 14. 試用要素

普段使わないクラスを試す機会を意図的に作る。

| 要素 | 概要 |
| ---- | ---- |
| **傭兵加入** | ランダム classId の一時メンバー加入 |
| **研究成果** | 特定 classId 専用のルール変化報酬 |
| **世界補正** | 特定 classId 関連 effect の大幅強化 |

傭兵の滞在期間（1 戦闘 / 1 層 / ラン全体）は未確定。

## 15. エンドレスモード

### 15.1 継続条件

ボス（またはランクリア条件）達成 **後も継続可能** とする。

### 15.2 目的

エンドレスも含め、目的は一貫して次のみ。

- 編成実験
- クラス研究
- 解法探索

**育成効率** や **メインモード用リソース farming** を目的にしない。

### 15.3 難易度

エンドレス継続中の問題難度・報酬品質の伸び方（線形 / 段階 / 上限）は未確定。

---

## 16. 長期ビジョン

「今日はどんな問題が出るだろう」を楽しむモードとする。

育成のために義務的に周回するのではなく、**解法探索そのものを遊び続ける** ためのコンテンツを目指す。

## 18. 実装フェーズ

**着手条件:** Phase 9（メインモードの globalExp・強化ツリー・Electron）完了後。メイン進行・クラスマスタ・戦闘基盤が安定してから、本モードを **Phase 10** として実装する。

**実装:** （未着手）— 本節は概要のみ。詳細タスクは [phase-roadmap.md](../plans/phase-roadmap.md) Phase 10 を参照。

### 18.1 スコープ（Phase 10 想定）

| 領域 | 内容 |
| ---- | ---- |
| **ラン状態** | メイン `SaveGameState` と分離したラン専用 state。シード・層・所持報酬・制約 |
| **問題生成** | 敵構成・傾向・ステージ補正の生成器 + データ定義（`data/roguelike/` 等、パスは実装時確定） |
| **マップ** | ノードグラフ生成・進路選択 UI |
| **報酬** | ルール変化型報酬の effect 適用（既存 battle effect 拡張またはラン Mod 層） |
| **世界補正・制約** | ラン開始 / ノード開始時の Mod 適用 |
| **編成** | 解放済み classId・ラン内パーティ上限。傭兵スロット |
| **戦闘** | 既存 `BattleEngine` 再利用。ラン Mod を戦闘コンテキストへ注入 |
| **エンドレス** | クリア後の難度スケールと報酬テーブル |
| **UI** | マップ・報酬選択・ラン結果。メインモード入口 |

### 18.2 スコープ外（Phase 10 初期）

- メインモードへのラン報酬の永続転用
- ラン専用の新クラス追加
- 戦闘中のプレイヤー操作
- アイテム・装備・ショップインベントリ（プロジェクト全体スコープ外と同様）

### 18.3 依存関係

```text
Phase 8（バランス + 印術師・法陣師）
    ↓
Phase 9（globalExp + 強化ツリー + Electron）
    ↓
Phase 10（ローグライクモード — 本 spec）
```

### 18.4 受け入れ基準（概要）

- メインモードと独立したランが開始〜敗北/クリアまで完走できる
- プレイヤー操作が編成・報酬選択・進路選択のみである
- 少なくとも 1 種類の世界補正・制約・クラスルール変化報酬が機能する
- エンドレス継続時も §15 の目的（解法探索）に沿い、メイン育成への依存がない
- 自動戦闘は [combat.md](combat.md) の確定結果レイヤーと矛盾しない

### 18.5 データ・ spec 同期

新規 effect・モディファイア・JSON スキーマを追加する場合は、同 Phase 内で [classes-and-skills.md](classes-and-skills.md) / [combat.md](combat.md) およびスキルデータ編集ツール（`.cursor/rules/skill-data-editor-sync.mdc`）を同期する。
