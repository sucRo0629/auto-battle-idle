# 作戦ループ（Wave 作戦）

実装：**R5 以降**（本書は上位仕様のみ。データ責務は [combat-data-schema-refactor.md](../plans/combat-data-schema-refactor.md)。具体的な型・所有クラス・実装ファイルは R5 へ送る）

本ドキュメントは **複数 Wave を通した 1 回の攻略単位（作戦）** の進行正本。座標・接敵・BattlePhase FSM の legacy 説明は [battle-field.md](battle-field.md)。Attack / Hit・DoT・一時効果の戦闘ルールは [combat.md](combat.md)。作戦外の恒久進行は [progression.md](progression.md)。

**R3 確定（2026-07-12）:** 作戦状態と戦闘状態の分離、Wave 間全回復、戦闘方式の Wave 間持ち越し、Wave 開始チェックポイント、3 種リトライ、作戦途中セーブなし。

**R12a 確定（2026-07-15）:** Wave 勝利条件＝敵全滅（ゲームルール）。敵問題・戦術目標・敗因の識別可能性は [§15](#15-敵問題と戦術目標r12a)。

**R12b 確定（2026-07-15）:** 1 Wave 単位の敵問題成立条件・敵側戦術（保護 / 分担 / 相乗）は [§16](#16-1-wave-単位の敵問題r12b)。

**R12c 確定（2026-07-15）:** 作戦全体の敵問題・Wave 間関係（継続 / 転換 / 複合 / 対立）は [§17](#17-作戦全体の敵問題r12c)。

## 1. 用語（プレイヤー向け）

| 用語 | 意味 |
| ---- | ---- |
| **作戦** | 複数 Wave を通した 1 回の攻略単位 |
| **Wave** | 作戦内の個別戦闘 |
| **初期準備** | Wave 1 開始前の編成・戦闘方式選択・出撃確定 |
| **Wave 間準備** | Wave 2 以降の各 Wave 開始前に行う準備（単なる短い BattlePhase ではない） |
| **作戦結果** | 最終 Wave 終了後の結果画面・恒久反映の境界 |

**採用しない正本用語:** 「ラン」「ローグライク」「ノード」など旧 [roguelike-mode.md](roguelike-mode.md) 由来の呼び方。

内部名称（クラス名・enum・Save キー等）は **R5 実装時に subset 確定**（データ責務は [combat-data-schema-refactor.md](../plans/combat-data-schema-refactor.md)）。

## 2. 上位ループ

```
初期準備
  → Wave 戦闘
  → Wave 終了
  → （最終 Wave でなければ）Wave 間準備
  → 次 Wave 戦闘
  → …
  → 最終 Wave 終了
  → 作戦結果
```

**原則:**

- **Wave 間準備**は編成画面・戦闘方式選択・作戦内状態・リトライを跨ぐ **上位進行状態** として扱う。
- **`BattleEngine` だけで完結させない。** 準備画面は戦闘外のゲーム状態として実装する可能性が高い（[battle-field.md §Wave 作戦と legacy BattlePhase](battle-field.md#wave-作戦と-legacy-battlephase)）。
- Wave 戦闘中は **直接操作なし** を維持（[combat-architecture.md](../combat-architecture.md) §0 と整合）。
- 戦闘速度変更・ポーズの詳細は **R7**。R3 では上位導線のみ [§8](#8-リトライ導線r7-接続) に記載。

## 3. 作戦状態と戦闘状態の分離

作戦状態と戦闘状態を **同じ保存オブジェクトへ無制限に混在させない** ことを原則とする。所有クラス・型・永続化形式は **R4 以降**。

### 3.1 作戦状態（複数 Wave を通して保持）

| 候補フィールド | 内容 |
| -------------- | ---- |
| 現在の作戦 ID | 選択した作戦（旧「ステージ」に相当しうるが 1:1 固定しない） |
| 現在の Wave 番号 / Wave ID | いま挑戦中または準備中の Wave |
| クリア済み Wave | 作戦内で勝利確定した Wave の記録 |
| 現在の編成 | 味方 4 兵科（同一兵科禁止） |
| 各兵科の選択中戦闘方式 | Wave 間で保持。毎 Wave 未選択へ戻さない |
| 取得済み作戦内パッシブ | 作戦終了まで維持（取得 UI・コストは R8 / R11c） |
| 未使用作戦内リソース | 入手量・タイミングは未確定 |
| Wave 開始チェックポイント | [§7](#7-wave-開始チェックポイント) |
| 作戦固有ルール | ステージ / 作戦定義由来の modifier |

### 3.2 戦闘状態（Wave 開始時に生成、Wave 終了時に破棄または初期化）

| 候補フィールド | 内容 |
| -------------- | ---- |
| Combatant | 味方・敵ユニット runtime |
| HP / Barrier | Wave 内の生存・シールド |
| DoT / HoT | 継続効果 |
| CC | 行動制限等 |
| 現在ターゲット | chase / attack 解決結果 |
| 位置（`battleX` 等） | フィールド上配置 |
| Attack timer | 攻撃間隔カウント |
| 一時バフ / デバフ | Wave 内限定 |
| 戦闘内カウンタ | per-Wave フラグ等 |
| 一時オブジェクト | projectile / field 等 |

Wave 開始時: 作戦状態から **編成・戦闘方式・作戦内パッシブ** を戦闘へ反映し、上記戦闘状態を新規構築する。

Wave 終了時: 戦闘状態を確定・破棄し、作戦状態へ **クリア記録・報酬候補** のみを反映する。

## 4. 初期準備（Wave 1 前）

Wave 1 開始前に、最低限次を行える **上位仕様**:

| 項目 | 内容 |
| ---- | ---- |
| 作戦情報の確認 | 作戦名・Wave 数等（開示範囲の詳細は未確定） |
| Wave 1 の敵情報確認 | 敵編成の事前確認 |
| 味方 4 兵科の編成 | 空きスロット不可（出撃時 4 人前提） |
| 同一兵科重複の禁止 | 味方編成全体で 1 兵科 1 体まで |
| 各兵科の戦闘方式選択 | 兵科ごとに 2 方式から 1 つ |
| 出撃確定 | 次状態へ遷移する明示的操作 |

**未確定:** 作戦内パッシブ取得を初期準備でも可能にするか。

**R6 以降（UI Phase）:** 編成・戦闘方式のデフォルト値、出撃ボタン有効条件、初回ガイド、画面レイアウト。

## 5. Wave 戦闘

### 5.1 Wave 開始時の反映

作戦状態 → 戦闘状態へ反映する項目:

| 項目 | 備考 |
| ---- | ---- |
| 現在の編成 | |
| 各兵科の戦闘方式 | |
| 取得済み作戦内パッシブ | R8 で実装 |
| Wave 固有の敵編成 | |
| Wave 固有ルール | ステージ / Wave 定義 |

敵側の **戦闘方式・所持パッシブ** も Wave 開始時に戦闘へ反映するが、**データ構造は R4** へ送る。

### 5.2 戦闘中

- 直接操作なし。観察用の **一時停止** と **倍速（最小 UI）** は [battle-field.md §8.11](battle-field.md#8111-戦闘一時停止観察-ui--phase-4-task-1) / [§8.11.1a](battle-field.md#8111a-戦闘倍速最小-ui--r7b) 参照（R7b）。
- 座標・接敵・描画は [battle-field.md](battle-field.md) の戦闘フィールド節（legacy BattlePhase 含む）が現行実装説明。新ループ置換後も **1 Wave 内の戦闘 sim** として再利用する想定。

### 5.3 Wave 終了判定

最低限、次を **区別** する:

| 結果 | 概要 |
| ---- | ---- |
| **Wave 勝利** | 当該 Wave の勝利条件達成（[§5.3.1](#531-wave-勝利条件r12a)） |
| **Wave 敗北** | 当該 Wave の敗北条件達成 |
| **timeout / 異常終了** | 時間切れ・内部エラー等（扱いは未確定） |
| **最終 Wave 勝利** | 作戦内最後の Wave をクリア |

#### 5.3.1 Wave 勝利条件（R12a）

**Wave の勝利条件は敵全滅で固定する。**

これは **ゲームルール** であり、[§15 敵問題](#15-敵問題と戦術目標r12a) ではない。敵問題は勝利条件そのものを定義せず、勝利条件の達成過程でプレイヤーへ戦術課題を提示する。

#### Wave 勝利時

1. 戦闘 sim を停止
2. 戦闘状態を確定
3. 作戦状態へ Wave クリアを記録
4. 報酬・作戦内リソースの反映（**入手量・タイミングは未確定**）
5. 最終 Wave でなければ **Wave 間準備** へ
6. 最終 Wave なら **作戦結果** へ

#### Wave 敗北時

- **作戦全体を即終了させない**
- 現在 Wave の **再試行導線** を持つ（[§8](#8-リトライ導線r7-接続)）
- Wave 開始前の準備状態へ戻れる
- 作戦開始からのやり直しも可能

敗北時の自動遷移先は **R7 リトライ仕様** と接続できる形にしておく（確認ダイアログなし方針を維持）。

## 6. Wave 間準備

Wave 2 以降の各 Wave 開始前に入る **上位状態**。BattlePhase の 1 フェーズとして短く済ませない。

### 6.1 将来扱う項目（R3 では UI 未確定）

| 項目 | 備考 |
| ---- | ---- |
| 次 Wave の敵情報確認 | 開示範囲は未確定 |
| 編成変更 | |
| 戦闘方式変更 | 前 Wave から **そのまま保持**。ここで変更可能 |
| 作戦内パッシブ取得 | **R8 / R11b**。直接指定。候補は作戦専用 ID |
| 未使用リソース確認 | |
| 出撃確定 | Wave 開始チェックポイント更新の境界 |
| 現在 Wave の再試行 | [§8](#8-リトライ導線r7-接続) |
| 作戦最初からの再開始 | [§8](#8-リトライ導線r7-接続) |

### 6.2 R3 で明示する禁止・方針

| 禁止 / 方針 | 理由 |
| ----------- | ---- |
| Wave 間準備に入っただけでパッシブを **自動取得しない** | プレイヤー直接指定方針 |
| **ランダム 3 択報酬を表示しない** | 旧 roguelike 報酬を採用しない |
| 作戦内パッシブ実装本体は **R8** | |
| **R6 最小 Wave 間準備** | 編成変更 + 戦闘方式変更だけで成立可能にする |

### 6.3 作戦内リソースとパッシブ取得コスト（R11c）

`data/operation-passive-catalog.json` が正本。

| 原則 | 内容 |
| ---- | ---- |
| 取得上限なし | 同じスロットへ候補を重複なく追加できる限り、取得回数に hard cap は無い |
| コスト式 | `cost = base(unlockLevel) + n × sameClassStackStep`（`n` = 取得前の同一スロット取得数） |
| unlockLevel | **コスト帯のみ**（パーティ Lv ゲートではない）。`costUnlockLevelByPassiveId` → `unlockLevelCostTable` |
| Wave クリア付与 | `waveClearResourceGrant`（≈ 6 人分 × 1〜2 回の初回帯購入）。中間 Wave クリア時に一度付与 |
| フォールバック | 候補の unlockLevel 欠損時は `passiveAcquireCost` |

実装: `src/game/operationPassiveAcquireCost.ts` / `GameSession.tryAcquireOperationPassive`。

## 7. Wave 間の回復・状態リセット

[combat.md §Wave 間状態リセット候補](combat.md#wave-間状態リセット候補) の候補を、R3 では **初期方針** として正本化する。

### 7.1 Wave 終了時にリセット（戦闘状態）

| 項目 |
| ---- |
| HP — **全回復**（採用。下記 §7.3） |
| Barrier |
| DoT |
| HoT |
| CC |
| current target |
| 位置（`battleX` 等） |
| Attack timer |
| 一時バフ / デバフ |
| 戦闘中カウンタ |
| 一時オブジェクト（projectile / field 等） |

### 7.2 作戦中維持（作戦状態）

| 項目 |
| ---- |
| 編成 |
| 戦闘方式選択（次 Wave へ **そのまま保持**。準備画面で変更可） |
| 取得済み作戦内パッシブ |
| 未使用リソース |
| クリア済み Wave |

### 7.3 HP 全回復の採否（R3 確定）

**採用:** 各 Wave を **独立した編成問題** として扱うため、Wave 終了（または次 Wave 開始）時に **HP は全回復** する。

- 前 Wave の損耗を持ち越す **長期消耗戦** にはしない。
- 作戦を通した成長・判断は **作戦内パッシブ** と **未使用リソース** で表現する。

**戦闘方式:** 次 Wave へ **そのまま保持** する。毎 Wave 未選択へ戻さない。変更は Wave 間準備（または初期準備）で行う。

## 8. Wave 開始チェックポイント

現在 Wave を **準備段階から再試行** するため、**Wave 開始直前**（出撃確定時点）の作戦状態をチェックポイントとする。

### 8.1 チェックポイントに含める候補

| 項目 |
| ---- |
| 現在 Wave |
| 編成 |
| 戦闘方式 |
| 取得済みパッシブ |
| 未使用リソース |
| クリア済み Wave |
| Wave 開始前に確定した取得・消費 |

### 8.2 再試行時の原則

| 原則 | 内容 |
| ---- | ---- |
| 戦闘中の変化は破棄 | 敗北時に HP・DoT 等を作戦状態へ書き戻さない |
| チェックポイントを復元 | 出撃確定時点の作戦状態へ |
| 遷移先 | Wave 間準備、または出撃直前 |
| 過去 Wave | **再戦しない**（クリア済み Wave は維持） |

### 8.3 パッシブ・リソースの巻き戻し（R3 確定）

**推奨を正本化:** チェックポイントは **出撃確定時点**。

- 出撃 **前** に行ったパッシブ取得・リソース消費は、Wave 敗北後の再試行でも **維持** する。
- Wave **戦闘中** に得たものは再試行で破棄（戦闘状態側）。
- 別の取得に変更したい場合の **取り消し・再購入** は **R8** へ送る。

具体的なコピー方式・永続化・メモリ表現は **R4 以降**。

## 9. リトライ導線（R7 接続）

R7 で実装する 3 種類 + 作戦中断。作戦状態・チェックポイントと整合させる。

**到達可能な入口:** 敗北 retry overlay・**戦闘ポーズ銘板（Wave 戦闘中）**・Wave 間準備。

| 種類 | 挙動 | チェックポイント |
| ---- | ---- | ---------------- |
| **同じ設定で再戦** | 現在 Wave を同じ編成・同じ戦闘方式・同じパッシブで **即再戦** | Wave 開始チェックポイントを使用 |
| **準備へ戻る** | 現在 Wave の準備へ。編成・戦闘方式を変更可能 | クリア済み Wave は維持。パッシブ変更可否は R8 |
| **作戦を最初から** | Wave 1 前の **初期準備** へ。作戦内パッシブ・リソース・クリア済み Wave を初期化 | 恒久解禁・作戦外記録は消さない |
| **ステージ選択へ** | 未完了 Operation を **破棄** し `stageSelect` へ | checkpoint 破棄。`currentStageId` は維持 |

- Wave **戦闘中**もポーズから上記へ入れる（敗北を待たない）。
- **確認ダイアログを挟まない** 方針を維持。
- UI 上のボタン名は未確定。

## 10. 作戦完了（最終 Wave 勝利）

| 手順 | 内容 |
| ---- | ---- |
| 1 | 作戦クリアを記録（作戦外進行へ反映する候補） |
| 2 | 作戦内状態を終了 |
| 3 | **作戦結果** へ遷移（verify OFF: battle 上の最小 overlay。verify ON: 非表示・従来 loop） |
| 4 | 作戦内パッシブ・未使用リソースは **破棄** |
| 5 | 恒久的なクリア記録・兵科解禁等があれば **作戦外進行** へ反映（結果 UI **表示前** に適用） |

**R7e 最小 UI（verify OFF）:** `outcome`・`stageId`・`reachedWaveIndex` を表示。操作は **同じステージで再戦**（Wave 0・formation 経由）と **ステージ選択へ**。報酬一覧・スコア・演出は未実装。

**採用しない:** 旧 `demo_ch1_07` の弩砲士解禁など、既存報酬を新仕様へ **そのまま継承しない**。恒久解禁・報酬設計は後続 Phase へ送る。

## 11. 作戦途中セーブ（R3 確定）

**初期縦切り（R5）では作戦途中セーブを実装しない。**

| 方針 | 内容 |
| ---- | ---- |
| 保持場所 | 作戦状態は **実行中メモリ** のみ |
| 終了 | アプリ終了・リロードで作戦終了してよい |
| 自動保存 | しない |
| 中断復帰 UI | 作らない |
| Save migration | 作戦途中状態を初期実装に含めない |

**設計候補:** 恒久的なクリア記録・解禁は **作戦完了時** に既存 Save へ保存できる。

**保留:** 中断セーブは試作成立（R10 以降）後の再検討事項として残す。

## 12. 作戦外進行との関係

進行の 3 層は [progression.md §進行の 3 層（R3）](progression.md#進行の-3-層r3) を正本とする。

| 層 | 本書での位置づけ |
| -- | ---------------- |
| 作戦外進行 | 作戦選択・クリア記録・恒久解禁 |
| 作戦内進行 | 本書 §3.1・§6・§7・§8 |
| Wave 戦闘 | 本書 §3.2・§5 |

**新仕様の原則（作戦選択）:**

- 作戦は **任意選択**
- 作戦内では **Wave 順** に進む
- 作戦選択順は **固定しない**
- 作戦敗北で **別作戦の選択状態を巻き戻さない**

## 15. 敵問題と戦術目標（R12a）

反復可能な作戦・Wave を設計するときの **authoring 正本**（用語・最小構造）。1 Wave 単位の成立条件・敵側戦術は [§16](#16-1-wave-単位の敵問題r12b)。複数 Wave を通した作戦全体の敵問題・Wave 間関係は [§17](#17-作戦全体の敵問題r12c)。実装 API・JSON フィールド名・UI 文言は本節では定義しない。上位の設計思想は [enemy-design-concept.md](../enemy-design-concept.md) / [design-philosophy.md](../design-philosophy.md) を参照し、用語の正本は本書とする。

### 15.1 敵問題

**敵問題**とは、敵編成・敵戦闘方式・Wave 構成によって、プレイヤーへ戦術目標を提示し、その達成方法の選択と代償を考えさせる構造である。

[§5.3.1](#531-wave-勝利条件r12a) の勝利条件（敵全滅）とは別概念である。勝利条件はゲームルールであり、戦術目標ではない。

### 15.2 戦術目標

**戦術目標**とは、Wave 内の敵全滅という勝利条件を達成するために、その敵問題でプレイヤーが解決しなければならない課題である。

| 扱い | 内容 |
| ---- | ---- |
| 設計上の位置づけ | **設計用の内部概念** |
| 通常プレイ | **直接表示しない** |
| 攻略支援 | 同一問題で複数回敗北し試行が停滞した場合、段階的に提示してよい |

### 15.3 戦術目標の最小属性

戦術目標は次の **3 属性** で構成する。

| 属性 | 内容 |
| ---- | ---- |
| **対象** | 何に対して課題が掛かるか |
| **目標状態** | 対象が満たすべき状態。「排除する」「維持する」「突破する」などの動詞は、目標状態を文章化した表現として扱う |
| **期限・成立時点** | いつまでに／どの時点で成立とみなすか。**固有期限がない場合の既定値は Wave クリアまで** |

### 15.4 戦術目標数

- 敵問題は **1 つ以上** の戦術目標を持つ。
- **上限は設けない**。
- 難易度や設計意図に応じて複数持ってよい。

### 15.5 敵問題の 5 要素（二層構造）

5 要素は、**戦術目標単位**と**敵問題全体**の二層で記述する。

各戦術目標に対応して、次を持つ。

1. **戦術目標**
2. **戦術目標未達時の敗北原因**
3. **有効な対処**
4. **対処に伴う代償**
5. **敗因の識別可能性**

### 15.6 敵問題全体が持つもの

敵問題全体では、次を持つ。

- 戦術目標同士の関係
- 支配的敗因
- 対処間競合
- 代償
- 全体としての敗因の識別可能性

### 15.7 敗因の識別可能性

**敗因の識別可能性**とは、プレイヤーが戦闘経過と結果から、満たせなかった戦術目標または支配的敗因について合理的な仮説を立て、次回変更する要素を決め、再挑戦によってその仮説を支持・否定・更新できる性質を指す。

| 含む | 含まない |
| ---- | -------- |
| 推測可能性 | UI 表示そのものではない |
| 検証可能性 | |

## 16. 1 Wave 単位の敵問題（R12b）

本節は [§15](#15-敵問題と戦術目標r12a) の枠組みに沿い、**1 Wave 単位**の敵問題と敵側戦術の抽象構造を定義する。実装 API・JSON・具体クラス能力・実データは定義しない。

### 16.1 戦術目標の成立時点

- 戦術目標は、**Wave 開始時点ですべて成立している**。
- 戦闘途中で新しい戦術目標が追加される構造は、R12b の基本形には含めない。
- 戦闘経過によって支配的敗因や達成状況が変化することはあるが、戦術目標自体が後から新設されるわけではない。

### 16.2 事前予測可能性

戦術目標は、Wave 開始前に提示された敵編成および敵戦闘方式から **合理的に予測可能** でなければならない。

Hensei-Only では、プレイヤーが事前の敵情報を読み、味方編成や戦闘方式を決めるためである。

| 求めること | 求めないこと |
| ---------- | ------------ |
| どのような課題が存在しそうかについて合理的な仮説を立てられること | 事前情報から正しい対処を一意に特定できること |

### 16.3 複数戦術目標の関係

複数の戦術目標は、それぞれ **個別に記述・判定可能** でなければならない。

ただし、実際の戦況では次を通じて相互作用してよい。

- 達成期限
- 敗北原因
- 有効な対処
- 対処に伴う代償
- 支配的敗因の移動

「独立」とは互いに無関係という意味ではなく、各課題の対象・目標状態・期限を個別に説明できることを指す。

### 16.4 敵数の最低条件

1 Wave の敵問題は、**最低 2 体以上** の敵によって構成する。

敵 1 体は、高火力、高耐久、回復、軽減、対象選択などの問題要素を提供できるが、単独では戦術目標を成立させない。敵 1 体だけの Wave は、原則として単純な火力検査または耐久検査に留まるため、R12b の敵問題として扱わない。

敵が 2 体以上存在するだけでは成立条件を満たさない。複数の敵が **敵側戦術** として機能し、プレイヤーの敵全滅を妨げる構造が必要である。

### 16.5 敵側戦術

**敵側戦術**とは、複数の敵要素が役割を組み合わせ、プレイヤーによる Wave 内敵全滅を妨げ、1 つ以上の戦術目標を発生させる構造である。

単なる敵の併置、数値の加算、戦況に影響しない能力の組み合わせは敵側戦術として扱わない。

敵側戦術は、少なくとも次を満たす必要がある。

- 複数の敵要素が組み合わさっている
- 単独配置とは異なる戦況を生む
- プレイヤーへ戦術目標を発生させる
- 放置すると敗北原因につながる
- 関連する対処変更によって戦闘経過が変わる

### 16.6 敵側戦術の基本分類

敵側戦術の基本分類は、次の **3 種** とする。

#### 保護戦術

ある敵要素が、重要な別の敵要素の処理を妨げ、その活動時間を延ばす戦術。

保護手段には、配置、耐久、回復、軽減、対象誘導などを含み得る。

本質は、処理したい重要要素を長く機能させることにある。

#### 分担戦術

複数の敵要素が異なる対応を同時に要求し、プレイヤーの限られた対応力を分散させる戦術。

異なる圧力対象、耐久要求、突破特性、単体処理、多数処理などを同時に要求する構造を含む。

各圧力が個別に無視できず、一方への対応が他方への対応力を実質的に下げる必要がある。

#### 相乗戦術

複数の敵要素が連携し、それぞれを単独で配置した場合には存在しない、または著しく弱い新しい圧力を発生させる戦術。

状態の付与と利用、弱体化と高火力、条件生成と条件特効などを将来的な例として含み得る。

具体的な能力設計は本節では行わない。

### 16.7 敵側戦術数

- 1 Wave は、保護・分担・相乗のいずれかの敵側戦術を、**少なくとも 1 つ** 持たなければならない。
- 複数の敵側戦術を同時に持ってよい。
- 競合する複数圧力を必須とはしない。
- 単一の保護戦術または相乗戦術であっても、戦術目標、対処、代償および敗因の識別可能性が成立するなら、1 Wave の敵問題として認める。
- 敵側戦術の分類が存在するだけでは Wave 成立条件を満たさない。

### 16.8 1 Wave の成立条件

1 Wave の敵問題は、次のすべてを満たさなければならない。

1. Wave 開始前に敵編成と敵戦闘方式が確定している
2. 敵が 2 体以上存在する
3. 敵側戦術が 1 つ以上存在する
4. 事前情報から予測可能な戦術目標が 1 つ以上存在する
5. 各戦術目標に、未達時の敗北原因が存在する
6. プレイヤーの選択によって達成状況を改善できる有効な対処が存在する
7. 有効な対処に、同一 Wave 内で実質的な代償が存在する
8. 関連する対処変更によって、戦術目標の達成状況または敗北過程に観測可能な差が生じる
9. 敗北時に、未達だった戦術目標または支配的敗因について合理的な仮説を立てられる
10. すべての戦術目標を代償なく改善する万能対処だけで解ける構造ではない

### 16.9 対処変更後に必要な結果差

有効な対処へ変更した結果、勝利まで変化することを必須とはしない。

少なくとも次のいずれかが変化すれば、検証可能な差として扱う。

- 戦術目標を達成できるようになる
- 戦術目標の達成時点が早まる
- 支配的敗因の発生が遅れる
- 観測可能な破綻が軽減される
- 最初に破綻する戦術目標が変わる
- 支配的敗因が別の戦術目標へ移る

どの選択でも同じ順序、同じ時点、同じ形で敗北する場合、その対処は有効に機能していない。

### 16.10 R12b で成立しない代表例

次は 1 Wave の敵問題として扱わない。

- 敵 1 体だけの Wave
- 同じ敵を複数並べただけで戦術上の相互作用がない
- 片方の敵が戦況へ実質的に影響しない
- 敵側戦術が名目上存在するだけで、戦術目標を発生させない
- 戦術目標を無視しても通常編成で勝てる
- 正しい対処が存在しない
- 対処を変えても戦闘経過が変わらない
- 代償のない万能対処ですべて解決できる
- 高 HP・高 ATK だけで勝敗を決める
- 敗因候補を絞れず、再挑戦しても仮説を更新できない

### 16.11 後続フェーズで再設計する事項

本章は、1 Wave の敵問題と敵側戦術の抽象構造を定義する。次の具体設計は R12b では確定しない。

- 各クラスが実現する敵側戦術
- 現行 R5 対象クラスとの対応付け
- 将来追加される全クラスの能力
- 敵用 CombatModule
- 作戦内パッシブ
- クラスごとの対象選択や戦闘挙動
- 数値、敵数、HP、ATK、取得コスト
- 実際の Stage・Wave データ

具体的なクラス能力、CombatModule、作戦内パッシブおよび敵データは、**後続フェーズで本章の敵側戦術と Wave 成立条件を満たすよう再設計する**。

敵側戦術の分類採否は、現行クラス能力で実現可能かどうかを根拠としない。

## 17. 作戦全体の敵問題（R12c）

本節は [§15](#15-敵問題と戦術目標r12a) / [§16](#16-1-wave-単位の敵問題r12b) の枠組みに沿い、**複数 Wave を通した 1 作戦**の敵問題と Wave 間関係を定義する。実装 API・JSON・具体クラス能力・数値バランス・実 Stage データは定義しない。

### 17.1 作戦全体の敵問題の定義

**作戦全体の敵問題**とは、各 Wave の敵問題を、**Wave 間関係**によって接続した構造である。

各 Wave が [§16.8](#168-1-wave-の成立条件) の 1 Wave 成立条件を個別に満たしているだけでは不十分である。作戦全体として、Wave をまたぐ判断差が生じなければならない。

| 概念 | 位置づけ |
| ---- | -------- |
| Wave 勝利条件（敵全滅） | ゲームルール（[§5.3.1](#531-wave-勝利条件r12a)） |
| 1 Wave の敵問題 | [§16](#16-1-wave-単位の敵問題r12b) |
| 作戦全体の敵問題 | 本節。Wave 間関係で接続された複数 Wave の構造 |

### 17.2 作戦全体としての成立条件

1 作戦の敵問題は、次のすべてを満たさなければならない。

1. 各 Wave が [§16.8](#168-1-wave-の成立条件) の 1 Wave 成立条件を満たしている
2. Wave 間に [§17.3](#173-wave-間関係) の **継続** / **転換** / **複合** / **対立** のいずれかが **1 種類以上** 存在する（4 種類すべてを必須とはしない）
3. 作戦開始前に開示された全 Wave の敵編成から、作戦全体として何が求められるか **合理的に推測できる**
4. 編成変更または戦闘方式変更を **検討する理由** が存在する
5. 作戦ポイントの **集中** と **分散** に、作戦全体として実質的な **代償** がある
6. Wave ごとに戦術目標が完全転換する構成を採用する場合、それが Wave 間関係として説明できる
7. 通常 Stage の最終 Wave が、過去 Wave で提示した敵側戦術または戦術目標を **統合した複合問題** である（[§17.9](#179-最終-wave-の複合問題)）
8. 作戦失敗時または特定 Wave 失敗時に、**未処理の戦術目標** を識別できる（[§17.10](#1710-敗因の識別)）
9. 全 Stage を同一編成で攻略できる **万能編成** を前提にしていない（[§17.11](#1711-万能編成と作戦内汎用編成)）
10. 特定 Stage 内の全 Wave を同一編成で攻略することを **禁止条件** にしていない
11. Wave 間差が、単なる敵数増加または scale 増加だけで構成されていない
12. 現行クラス能力の制約から、必要な問題構造を縮小していない

### 17.3 Wave 間関係

**Wave 間関係**とは、隣接または作戦全体を通じた Wave 同士の戦術要求のつながりを指す。1 作戦には、少なくとも 1 種類以上の Wave 間関係を含める。4 種類すべてを必須とはしない。

#### 継続

前 Wave で提示した戦術要求、対処方針、または作戦内資源の使い方が、後続 Wave でも **意味を持ち続ける** 関係。

前 Wave で立てた仮説・投資・編成判断が、後続 Wave の準備または戦闘経過に影響し得る。後 Wave が前 Wave の延長として読めるが、同一内容の単純反復ではない。

#### 転換

Wave ごとに、戦術目標または主要な敵側戦術が **別系統へ切り替わる** 関係。

前 Wave と同じ兵科・同じ対処を継続して要求する必要はない。完全転換も、作戦全体の Wave 間関係として位置づける（[§17.8](#178-戦術目標の転換)）。

#### 複合

複数 Wave で提示した戦術要求が、後続 Wave または最終 Wave で **同時に、または相互作用する形で再提示される** 関係。

過去 Wave の敵編成をそのまま合算する意味ではない。過去に学習・推測させた複数の戦術要求を、同時または連動して処理させる構造である。

#### 対立

Wave 間で、前 Wave 向けの最適な準備・資源配分・編成判断が、後 Wave 向けの最適解と **競合する** 関係。

作戦全体の限られた判断枠（編成、戦闘方式、作戦ポイント配分）の中で、一方への対応が他方への対応力を実質的に下げる必要がある。

### 17.4 Wave 数の扱い

- **2 Wave 作戦** と **3 Wave 以上の作戦** で、作戦全体の成立基準そのものは **分けない**。
- 3 Wave 以上は、2 Wave より多くの Wave 間関係・判断・資源配分を扱える **高難度作戦** として扱う。
- Wave 数が多いこと自体を、作戦全体の成立条件には **しない**。

### 17.5 事前開示と推測

- 作戦開始前から、**全 Wave の敵編成** を開示する。
- **戦術目標そのもの** は文章で表示しない（[§15.2](#152-戦術目標)）。
- プレイヤーは敵編成と敵戦闘方式から、各 Wave の戦術目標および Wave 間関係を **推測** する。
- 戦術目標の対処方法を **一意に特定できる必要はない**（[§16.2](#162-事前予測可能性) と同型）。

### 17.6 Wave 間の編成変更

- Wave 間では、味方 **4 枠すべて** を変更できる。
- 編成変更自体に、回数制限・追加コスト・固定枠などを **設けない**。
- 作戦全体の判断差は、編成変更を **制限すること** ではなく、**敵問題** と **作戦ポイント配分** によって生じさせる。

### 17.7 作戦ポイントと集中・分散

作戦ポイントの配分によって、**特定兵科への集中強化** と **複数兵科への分散強化** の代償を作る。

| 扱い | 内容 |
| ---- | ---- |
| 付与タイミング | 原則として **Wave クリア後** に付与 |
| 高難度 Stage | **初期作戦ポイント** の配布を許容 |
| 本節で定義しないもの | 具体的な付与量、コスト、`stackStep`、数値バランス（→ **R12i**） |
| 本節で定義しないもの | 具体的なパッシブ内容と能力配分（→ **R12e〜g**） |

本節では、資源が **作戦全体の判断**（どこへ集中し、どこを犠牲にするか）にどう関与するかだけを定義する。

### 17.8 戦術目標の転換

- Wave ごとに、戦術目標が **完全に転換** する構成を許容する。
- 前 Wave と同じ兵科・同じ対処を継続して要求する必要はない。
- 完全転換も **転換** という Wave 間関係として、作戦全体に位置づける。

### 17.9 最終 Wave の複合問題

通常 Stage の最終 Wave は、原則として、過去 Wave で提示した敵側戦術または戦術目標を **統合した複合問題** とする。

| 原則 | 内容 |
| ---- | ---- |
| 禁止 | 単なる敵数増加や数値強化だけで最終 Wave を構成すること |
| 通常 Stage | 上記原則に対する **例外を設けない** |
| スコープ外 | ローグライク等、将来の別モードに関する例外設計 |

**過去 Wave の複合問題** とは、過去 Wave の敵編成をそのまま合算する意味 **ではない**。過去に学習・推測させた複数の戦術要求を、**同時または相互作用する形** で再提示することを指す。

### 17.10 敗因の識別

作戦失敗時または特定 Wave 失敗時に、**どの戦術目標を処理できなかったか** 識別できればよい。

| 扱い | 内容 |
| ---- | ---- |
| 単一原因 | 敗因を単一原因へ **固定する必要はない** |
| 支配的敗因 | 複数の戦術目標がある場合、支配的敗因が途中で **移動してもよい** |
| 根拠 | [§15.7](#157-敗因の識別可能性) / [§16.3](#163-複数戦術目標の関係) |

### 17.11 万能編成と作戦内汎用編成

次の 2 つを **区別** する。

#### 認めないもの（万能編成）

**全 Stage** を同一編成で攻略できる万能編成。

兵科変更や戦闘方式変更をほぼ必要とせず、すべての敵問題を処理できる編成は **成立させない**。

#### 許容するもの（作戦内汎用編成）

**特定 Stage** の全 Wave を同一編成で攻略できる編成。

これは通常の想定解に限定せず、やり込み、縛りプレイ、高度な別解として **許容** する。

したがって、各 Wave で **必ず** 編成変更を要求する必要はない。重要なのは、作戦全体の敵問題に対して **判断と代償** が成立していることである。

### 17.12 Stage 先行設計と後続フェーズ

[R12d](../plans/phase-roadmap.md#r12d--試作-stage-の敵問題設計) では、具体的な兵科能力から Stage を組み立て **ない**。先に次を設計する。

1. 各 Wave の敵問題
2. 各 Wave の敵側戦術
3. 戦術目標
4. Wave 間関係
5. 最終 Wave の複合構造
6. 想定される失敗理由
7. 必要となる判断の種類

その後、**R12e** で必要能力・対処能力を導出する。

#### 現行能力の扱い

- 現行クラス能力をすべて破棄する前提には **しない**。
- 現行能力はある程度継承しつつ、Stage 先行で導出した必要能力を既存兵科へ **統合** する。
- ただし、現行クラス能力だけで実現可能かどうかを、敵問題や Wave 間関係の **採否基準にしない**。
- 具体的な統合判断は **R12e〜g**。

### 17.13 作戦全体として成立しない代表例

次は作戦全体の敵問題として扱わない。

- Wave ごとに敵編成が違うだけで、戦術要求の **関係** がない
- 各 Wave が独立問題で、作戦全体としての **判断** がない
- 編成変更可能だが、変更する **理由** が存在しない
- 作戦ポイントをどこへ使っても結果が **ほぼ同じ**
- 最終 Wave が過去 Wave と **無関係** な新問題
- 最終 Wave が敵数または scale を増やした **だけ**
- 全 Stage を同じ編成で処理できる
- 反対に、各 Wave で **必ず** 編成変更しなければならないことを機械的条件にする
- 戦術目標を UI 文として **直接正解表示** する
- 現行クラスで実現できないことを理由に、必要な問題構造を **除外** する

### 17.14 R12d authoring 用チェック項目

試作 Stage の敵問題を設計するとき、次を確認する。

**各 Wave（§16 準拠）**

- [ ] 敵 2 体以上、敵側戦術 1 種類以上
- [ ] 事前情報から予測可能な戦術目標 1 つ以上
- [ ] 対処・代償・敗因の識別可能性が成立

**作戦全体（§17 準拠）**

- [ ] 全 Wave が §16.8 を満たす
- [ ] Wave 間関係（継続 / 転換 / 複合 / 対立）を 1 種類以上、文書化できる
- [ ] 全 Wave の敵編成から作戦全体の要求を事前推測できる
- [ ] 編成変更または戦闘方式変更を検討する理由がある
- [ ] 作戦ポイントの集中・分散に代償がある
- [ ] 完全転換を採用する場合、転換関係として説明できる
- [ ] 通常 Stage の最終 Wave が過去 Wave の戦術要求を統合する
- [ ] 敗北時に未処理の戦術目標を識別できる
- [ ] 全 Stage 共通の万能編成を前提にしていない
- [ ] 特定 Stage 内の同一編成攻略を禁止していない
- [ ] Wave 間差が敵数・scale 増加だけではない
- [ ] 現行能力の制約から問題構造を縮小していない

**Stage 先行（設計順）**

- [ ] 敵問題・Wave 間関係・判断種類を、能力・JSON より先に文書化した
- [ ] 必要能力の導出は R12e へ送っている

### 17.15 後続フェーズで確定する事項

本章は、作戦全体の敵問題と Wave 間関係の抽象構造を定義する。次の具体設計は R12c では確定しない。

- 試作 Stage の各 Wave 表・敵編成（→ **R12d**）
- 必要能力・対処能力の導出（→ **R12e**）
- 兵科・CombatModule・作戦内パッシブへの分配（→ **R12f**）
- class / module / passive データ（→ **R12g**）
- Stage / Wave JSON 実装（→ **R12h**）
- 作戦ポイント付与量、コスト、`stackStep`、scale（→ **R12i**）
- 手元プレイ成立確認（→ **R12j**）
