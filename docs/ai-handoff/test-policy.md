# テスト作成方針（全体）

**目的:** テストは「今の実装がこう動く」を固定するためではなく、**確定した仕様どおりか**を確かめるために書く。

**正本の位置:** 本ファイル。Cursor 常時ルール要約は [.cursor/rules/tests-not-proof.mdc](../../.cursor/rules/tests-not-proof.mdc)。  
CombatModule 兵科 M1/M2 の詳細は [combat-module-test-policy.md](combat-module-test-policy.md)（本方針の適用例）。

---

## 1. 作成の観点（正）

テストを書く／直すときの第一問は次とする。

> このケースは、**確定仕様**（`docs/spec/`・当該 Phase の確定事項・ユーザー確定指示）どおりか？

| 固定してよいもの | 固定してはいけないもの |
| ---------------- | ---------------------- |
| 仕様が定める入力条件・期待結果・不変条件 | 「たまたま今こうなっている」だけの出力 |
| プレイヤー導線・画面上の到達結果（Player 層） | 仕様と違う現行挙動を緑にするための期待値 |
| 構造差・到達可否・排他・禁止事項の有無 | 無意味な件数・呼び出し回数だけ |

数値本調整前は仮数値でよい。ただし仕様の **構造**（誰を選ぶ、どこで止まる、何が起きない、方式が排他か）は仮数値でも崩さない。

---

## 2. 不合格になる確認（これだけでは足りない）

領域を問わず、次だけで「仕様どおり」とみなさない。

- データ形状・フィールド存在・ID 文字列一致だけ
- registry / 配列の件数だけ
- モックの呼び出し回数・スパイ有無だけ
- 説明文・エラーメッセージ文字列だけを挙動の代替にする
- 内部関数が一度通ったことだけ（入口・導線・実結果が未確認）

形状・validation・editor round-trip は **補助**として書いてよい。本体は仕様上の **実結果**（選ばれた対象、位置、HP/状態変化、画面到達など）とセットにする。

---

## 3. 領域ごとの実結果の例

| 領域 | 実結果として確認する例 |
| ---- | ---------------------- |
| 戦闘・CombatModule | target 実体、Approach 位置、damage / Hit、排他、敵味方対称（詳細は [combat-module-test-policy.md](combat-module-test-policy.md)） |
| UI / 導線 | 指定操作のあと、想定画面・パネル・選択肢に届くこと |
| 編成・Operation | 選択後に戦闘側の解決結果が変わること（ID 切替 alone で終わらない） |
| editor | load → edit → save → reload で仕様上の重要フィールドが維持されること |
| validation | 仕様違反データが拒否され、正当データが通ること（メッセージだけを仕様の代替にしない） |

---

## 4. 仕様と実装が食い違うとき

1. **test 期待値を現行実装に合わせて通さない**
2. 誤りの所在を分類する
   - 正本（`docs/` / Phase 確定）
   - 実装
   - test（fixture・前提・誤解）
3. 正本か実装を直し、test は確定仕様に合わせる
4. 分類を完了報告に残す

「テストを緑にする」は目的ではない。「仕様どおりを証明する」が目的である。

---

## 5. 完了判定との関係

- テスト緑だけでは Phase / タスク完了にしない（[planning-rules.md §2](planning-rules.md#2-フェーズ完了条件の二層)、[tests-not-proof](../../.cursor/rules/tests-not-proof.mdc)）
- Backend 完了でも、Player 導線が仕様上必要なら Player 未完了と書く
- 報告ではパス数より **何を仕様どおりと保証したか** を書く

---

## 6. pre-existing failure

失敗を単に pre-existing と呼ばない。少なくとも次で区別する。

1. 基準 commit ですでに失敗する
2. 直前 Phase で発生した
3. 直前の同系列タスクで発生した
4. **今回**のタスクで発生した

skip で隠さない。今回と無関係な assertion のついで修正も禁止。今回が原因なら同タスクで直す。

---

## 7. production 経路が難しいとき

可能な範囲で本番に近い経路を使う。困難なら完了報告に次を書く。

- 困難な理由
- 代替した確認経路
- 未確認範囲

代替でも「仕様上の実結果」が残っていること。
