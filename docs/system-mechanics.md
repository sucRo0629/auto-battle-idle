# System Mechanics

この文書は、複数クラスが利用する戦闘メカニクスをシステム視点で整理する。

クラス個別のスキル、数値、習得レベル、JSON スキーマは [spec/classes-and-skills.md](spec/classes-and-skills.md) を正本とする。ダメージ式、回復、CD、ステータス効果の詳細は [spec/combat.md](spec/combat.md)、座標・接敵・Wave は [spec/battle-field.md](spec/battle-field.md)、戦闘全体の Kill / Flow / Survival 構造は [combat-architecture.md](combat-architecture.md) を参照する。

ここでは「どのクラスが何を持つか」ではなく、**複数クラスの個性付けに使われる共通ルール群**として扱う。

## 実装状態の読み方

| 状態           | 意味                                                                                          |
| -------------- | --------------------------------------------------------------------------------------------- |
| 実装済み       | spec に実装箇所または実装済み記述があり、現行システムの一部として扱われている                 |
| 設計済み未実装 | spec 上の設計はあるが、現行の実装・データ反映が未完了、または今回の整理で未実装として扱うもの |
| 構想段階       | 設計思想として記述されているが、詳細仕様・データ形状・アルゴリズムが未確定                    |
| 不明           | 既存ドキュメントから状態を判断できないもの                                                    |

本書では不明なものを推測で補完しない。

## 設計思想

現在の戦闘は、単一の DPS レースではなく **Kill / Flow / Survival** の 3 レイヤーで整理されている。

- Kill は、敵 HP を削る処理であり、敵の耐性・HP 状態・攻撃イベント構造に適合することで差分を作る。
- Flow は、位置、範囲、時間密度、対象構造など、戦闘条件そのものを変える。
- Survival は、被害の入口、回復、バリア、軽減、解除によって味方全滅までの時間を延ばす。

そのため、共通メカニクスは「火力を増やすための部品」だけではない。ターゲット選択、Hit 密度、チャージ方式、範囲形状、バリア、DoT、反撃などが、各クラスの役割を分けるための操作点になっている。

## Player Level

プレイヤーレベルは全クラス共通である。セーブ上は `playerProgress`（アカウント 1 本）を正本とし、メンバー個別 Lv は持たない（[progression.md](spec/progression.md) Phase 11）。

プレイヤーレベル上昇時、全クラスの解放状態が更新される。

| Lv | 解放状態 | 意味 |
| --- | -------- | ---- |
| 1 | 初期 passive / 初期 active | クラスの基礎機能レイヤーを成立させる |
| 10 | 全クラスの中級スキル解放 | 追加の Kill / Flow / Survival 影響を獲得する |
| 20 | 全クラス完成 | 上位効果または複合レイヤー影響を獲得する |
| 20 以降 | 全クラスのステータス上昇 | 攻略不能時の救済手段として扱う |

レベルは戦力値ではなく、クラス完成度を表す。

Lv20 でクラス完成とする。Lv20 以降はステータスのみ上昇し、理想的な攻略方法はレベル上昇ではなく編成変更である。

passive / active は付け替え・セット・装備変更ではなく、**習得構造**として扱う。

- 習得済み passive / active は、それぞれ常時戦闘参加する。
- プレイヤーがスキルを付け替えるビルド概念は持たない。
- ビルド差分は、`classes.json` の Lv 習得構造と、各スキルが担う Kill / Flow / Survival の組み合わせで決まる。
- UI 上のロール分類は表示・配置のための補助情報であり、スキル設計は機能レイヤーで説明する。

## Instant Lv20 Option

プレイヤーは任意で、全クラス Lv20 扱いを有効化できる。

用途は次の通り。

- 編成検証
- レベリング省略
- 開発者プレイ
- 周回削減

## Level Sync

ステージ推奨レベルへ同期するオプションを持つ。

たとえば推奨 Lv20 ステージでは、Lv35 Warrior を Lv20 Warrior として計算する。

目的は育成差を除外し、純粋な編成・戦略で攻略するためである。

## Stage Records

プレイヤーの攻略履歴を保存する。

本作はタイムアタックではなく、攻略理解度を評価する。

保存項目は次の通り。

- First Clear Level
- Lowest Clear Level
- Best Time
- Latest Party
- Level Sync Clear

### Record Example

Stage 5-12

First Clear Lv: 24

Lowest Clear Lv: 20

Best Time: 01:43

Latest Party:

- Warrior
- Defender
- Geomancer
- Healer
- Ballista

Level Sync Clear: ✓

### ソート順

デフォルト表示順は `Lowest Clear Level ASC`、次に `Best Time ASC` とする。

### 設計意図

最低クリアレベルを主達成指標とする。

クリアタイムは補助的な遊び方として扱う。

レベルシンククリアは高難度達成として扱う。

## 確率判定と確定結果

回避、ブロック、防御無視、確率反撃、Stage/Wave 開始時パッシブなどは `chance` を持ち得るが、確率は判定時の内部処理としてのみ扱う。

戦闘状態は常に次の遷移で解決する。

```text
未判定状態 → 判定 → 確定状態
```

- `chance` はスキル定義・パッシブ定義上の判定パラメータであり、戦闘状態として未判定のまま保持しない。
- 判定後は、成功 / 失敗、適用 / 非適用、発動 / 非発動のいずれかに必ず確定する。
- HP、barrier、StatusEffect、Threat、位置、BattleSnapshot、戦闘ログには確定結果のみを反映する。
- 最終ダメージ・回復量そのものには乱数ブレを置かない。

この整理は、[combat-architecture.md](combat-architecture.md) の「確定結果レイヤー」と [spec/combat.md](spec/combat.md) の「確率判定と確定状態」を正本とする。

## ターゲット選択システム

ターゲット選択は、スキルや通常攻撃が「誰を対象にするか」を決める仕組みである。基本構造は `TargetSpec` と `targetShape` の組み合わせで、まず対象プールを作り、射程で絞り、形状に従って命中対象を解決する。

### Target Intent

同じ `TargetSpec` でも、何のために対象を選ぶかで評価軸を分ける。

| Intent | 役割 | 距離 / Threat の扱い |
| ------ | ---- | -------------------- |
| `AttackTarget` | damage / heal / buff / debuff の実対象 | 射程内プールから選ぶ。敵の対プレイヤー通常対象は Threat 優先 |
| `MoveAnchor` | `move` の到達基準 | 射程外も anchor にできる。Threat ではなく使用者との `battleX` 距離 |
| `ChaseTarget` | 自動接近の追跡対象 | 敵は Threat、味方はスキル / 通常攻撃の target spec |
| `DisplayAnchor` | VFX・描画凍結用 | 戦闘判定へ逆流させない。実装: `CombatantState.engagedDisplayAnchorPlayerId`（`battleDisplay.ts` helper） |

これにより、Flow の移動が発生しても「移動先」「攻撃対象」「追跡対象」「表示基準」を同一概念へ潰さない。

### 主な選択軸

| 軸            | 例                                               | 状態     |
| ------------- | ------------------------------------------------ | -------- |
| 距離          | nearest / farthest / selfOrigin                  | 実装済み |
| ステータス    | HP / ATK / DEF / REG の highest / lowest / ratio | 実装済み |
| HP 割合       | 低 HP 割合、負傷味方                             | 実装済み |
| 攻撃種別      | melee / ranged / physical / magic                | 実装済み |
| 状態          | buff / debuff タグ保持対象                       | 実装済み |
| 高 MaxHP 対象 | ボス・強敵処理の設計概念                         | 要確認   |

物理 Kill の設計では、高 DEF、瀕死、遠隔、高 Max HP といった敵側の問題を別々の処理対象として扱う。これにより、Kill / Flow 主軸クラスの差分は単なる DPS 差ではなく「どの敵構造に適合するか」として表現される。

### ターゲット選択とターゲット特効

ターゲット選択とターゲット特効は別概念である。

| 概念           | 役割                                         | 例                                                                    |
| -------------- | -------------------------------------------- | --------------------------------------------------------------------- |
| ターゲット選択 | 攻撃・回復・バフ・デバフの対象を選ぶ         | 高 DEF 敵を狙う、HP 割合が低い味方を選ぶ、遠隔敵を優先する            |
| ターゲット特効 | 選ばれた対象が条件を満たすと効果量を増幅する | HP 割合が一定以下の対象へのダメージ増加、特定 debuff 中の対象への倍率 |

ターゲット選択は「当て先」を変える。ターゲット特効は「当たった後の効き方」を変える。たとえば低 HP の敵を優先することと、低 HP の敵に追加倍率を乗せることは組み合わせられるが、片方だけでも成立する。

処理対象を持つ Targeted Kill では、passive P1 がターゲット選択、P3 Lv10 がターゲット特効（処理対象特効）を担う設計ルールがある。枠割りの詳細は [classes-and-skills.md の Targeted Kill の passive 段階](spec/classes-and-skills.md#targeted-kill-の-passive-段階設計ルール) を正とする。

## スキルチャージシステム

アクティブは `trigger` によってチャージ方式が変わる。現在の設計では、時間だけでなく、通常攻撃や被弾をリソース化できる。

| 方式           | 進行条件                                     | 設計意図                                                 | 状態     |
| -------------- | -------------------------------------------- | -------------------------------------------------------- | -------- |
| 時間回復       | 時間経過で CD が進む                         | 安定した周期行動。通常攻撃の成否や被弾に依存しない基準型 | 実装済み |
| 攻撃回数回復   | 通常攻撃の damage ヒットごとに進む           | Hit 数・攻撃速度・通常攻撃変形を火力回転へ接続する       | 実装済み |
| 被攻撃回数回復 | 使用者が hurt になるたび進む                 | 被弾を防御・反撃・制圧の起点に変換する                   | 実装済み |
| 多段チャージ   | `maxCharges` と smart 保留によりストックする | 発動タイミングを条件待ちできる余地を作る                 | 実装済み |

カウント式は、ゲージ Max になった瞬間に自動発動するのではなく、次の消費イベントで発動する。攻撃回数式なら N 回目で準備完了、N+1 回目の通常攻撃枠で通常攻撃の代わりにアクティブが発動する。

この構造により、双刃士や弓術士のような Hit / 攻撃回数に依存するクラスは、単に通常攻撃が強いだけでなく、アクティブ回転そのものを変えられる。

## SkillHold

`useDurationSec` はデバフではなく、hold / channel / commit time 系スキルの特性である。定義はスキルデータ層に残し、戦闘エンジン層が実行時の SkillHold として処理する。

- スキルデータ層は `useDurationSec` により「このスキルは SkillHold を発生させる」と宣言する。
- 戦闘エンジン層は発動成功時に SkillHold を開始し、残時間、busy 判定、CD / イベントゲージ停止を管理する。
- 持続中は使用者自身の通常攻撃・アクティブ発動を止める。
- 持続中は使用者自身の basic CD / active CD / `basicAttackCount` / `hitsTaken` を停止する。
- スタン、`presentationLock`、`animLock` は SkillHold ではないため、CD を止めない。
- 敵対的な時間停止は `freeze` など別 `StatusEffect` として定義する。

## Hit システム

現在の設計では **Attack** と **Hit** は別概念である。

| 概念        | 意味                                                            |
| ----------- | --------------------------------------------------------------- |
| Attack      | 行動枠。通常攻撃やアクティブ発動など、ユニットが行う 1 回の行動 |
| Hit         | 効果適用イベント。1 回の Attack から 1 回以上発生し得る         |
| Skill Gauge | Hit や被弾などのイベントから進むアクティブ用リソース            |

この分離により、1 回攻撃で複数 Hit する、Hit ごとにチャージが進む、Hit ごとに VFX や追加効果が発生する、といった設計が可能になる。

主な利用先は次の通り。

- `hitCount` による同一対象または同一範囲への複数 Hit。
- `multiLock` による複数対象への Hit 配分。
- `hitDurationSec`、`chainDurationSec`、`scatterDurationSec` による Hit 適用タイミングの分散。
- `basicAttackCount` trigger による、通常攻撃 damage ヒットごとのゲージ加算。

Attack / Hit / Gauge の厳密な内部仕様は、`classes-and-skills.md` で未文書化項目としても挙げられている。一方で、`hitCount`、カウントトリガー、Hit 単位の適用分散は現行仕様として整理されている。

## 通常攻撃変形

通常攻撃変形は、スキル中またはバフ持続中に通常攻撃の effect を別挙動へ変換する仕組みである。`basicAttackTransform` は自身に付与され、持続中のみ通常攻撃の primary effect を実行時にマージする。

| 変形             | 内容                                         | 状態     |
| ---------------- | -------------------------------------------- | -------- |
| Hit 数変更       | 既存 primary の `hitCount` に倍率を掛ける    | 実装済み |
| primary 差し替え | 通常攻撃を damage から heal などへ差し替える | 実装済み |
| primary patch    | damageType や amount などを部分上書きする    | 実装済み |
| 追加効果         | primary の後に heal / debuff などを追加する  | 実装済み |

設計意図は、通常攻撃を単なる常時 DPS ではなく、クラスの時間構造を変える基盤にすることにある。たとえば 1 Hit から 2 Hit への変形は、ダメージだけでなく攻撃回数チャージにも影響する。一方で heal 化した通常攻撃は damage ヒットではないため、`basicAttackCount` の充填が止まる。

## ダメージ処理

ダメージ処理系メカニクスは、被害を「減らす」「受ける場所を変える」「受けるタイミングを変える」「攻撃へ変換する」ための共通ルールである。

| メカニクス     | 役割                                                                   | 状態     |
| -------------- | ---------------------------------------------------------------------- | -------- |
| Barrier        | HP の前に消費される別プール。直接ダメージ / DoT 共通で吸収する         | 実装済み |
| 被ダメージ軽減 | `damageTaken` や `damageReduction` により最終被ダメ倍率を変える        | 実装済み |
| Block          | 物理直接ダメージのみ、DEF 適用後に一部を防ぐ。魔法 block は Paladin 後半 passive 候補 | 物理 block は実装済み |
| Evasion        | 直接 damage を無効化する。DoT tick は対象外                            | 実装済み |
| Counter        | 被攻撃を起点に攻撃者へ damage / debuff / dot / stun / knockback を返す | 実装済み |
| DamageDelay    | 確定ダメージの一部を後払いにする。軽減ではなくタイミング変更           | 実装済み |

Barrier は Survival Layer の猶予を作る。被ダメージ軽減は損失量そのものを下げる。Counter は被弾を損失だけで終わらせず、制圧や反撃へ変換する。DamageDelay は総被ダメージ量を変えず、損失の時間分布を変えるメカニクスとして扱う。

## 状態異常・継続効果

状態異常と継続効果は、単発ダメージではなく時間や行動可否を操作するメカニクスである。

| 種別   | 役割                                             | 状態     |
| ------ | ------------------------------------------------ | -------- |
| DoT    | 1 秒ごとに damage tick を発生させる持続ダメージ  | 実装済み |
| HoT    | 1 秒ごとに heal tick を発生させる持続回復        | 実装済み |
| 出血   | DoT フレーバー `dotFlavor: bleed`（tick 式は DoT 共通） | 実装済み（v1） |
| 毒     | DoT フレーバー `dotFlavor: poison`（tick 式は DoT 共通） | 実装済み（v1） |
| Stun   | 行動不能 CC。使用者としての通常攻撃・アクティブ発動・ターゲット選択を止める。CD は止めない | 実装済み |
| Freeze / 時間停止系拘束 | CD 停止など時間進行へ干渉する上位制御。スタンとは別状態として扱う | 構想段階 |
| Dispel | debuff / DoT / stun などを指定数または全解除する | 実装済み |

出血と毒は、内部的に別ダメージ式を持たず、同一の DoT メカニクス（`overlay: dot`、1 秒 tick）に対する表示・フレーバー層として扱う。`debuffSubKind: dot` の effect に任意で `dotFlavor: bleed | poison` を指定し、未指定は従来どおり汎用 DoT。`DebuffFilterTag` の `bleed` / `poison` は各フレーバー専用、`dot` は全フレーバー + 未指定にマッチする。

**DoT 再付与:** buff/debuff / CC の `remainingSec` は長い方を採用するが、**DoT（`overlay: dot`）のみ例外** — 再付与時にマージせず StatusEffect を追加し、各实例が独立 tick（累積）する。詳細は [combat.md](spec/combat.md) §状態再付与。

**狩猟士（`at_hunter`）:** Physical pass B **実装済**。Field Flow 職として `placedField`（`clusterCenter` 配置）による局所 poison Field、`dotCompress` / `dotExtend` / `dotHarvest`、`hasDot` 条件、P2 味方 basic からの poison 付与を扱う。広範囲 DoT 火力や scatter 罠は v1 主軸にしない。視界妨害・命中干渉・フィールド端貫通は v1 外。

Stun は damage ではなく行動可否を操作する。スタン中は使用者として通常攻撃・アクティブが発動せず、ターゲット選択も行わない。一方で CD は戦闘時間に従って進行し続ける。時間 CD 停止や時間進行そのものへの干渉が必要な場合は、Freeze / 時間停止系拘束など、スタンとは別の状態として定義する。

## ダメージ拡張

ダメージ拡張は、単に ATK を上げるのではなく、耐性軸・被ダメ軸・条件適合を通じて実効ダメージを変えるメカニクスである。

| メカニクス     | 内容                                                          | 状態     |
| -------------- | ------------------------------------------------------------- | -------- |
| DEF 貫通       | 物理ダメージの DEF を flat / percent で無視する               | 実装済み |
| REG 貫通       | 魔法ダメージの REG を percent で無視する                      | 実装済み |
| REG 低下       | `reg` debuff により魔法耐性を下げる                           | 実装済み |
| 被ダメージ増加 | `damageTaken` debuff により対象の被ダメ倍率を上げる           | 実装済み |
| 特効           | 対象 HP 条件や debuff 条件などで damage / heal に倍率を乗せる | 実装済み |
| crowd bonus    | AoE / scatter の追加命中数に応じて威力を調整する              | 実装済み |
| power step     | chain / pierce の段階ごとに威力を減衰・調整する               | 実装済み |

DEF / REG 貫通は耐性軸への介入であり、被ダメージ増加は対象側の最終被ダメ倍率への介入である。特効は条件適合を表し、ターゲット選択とは独立している。

この分離により、高 DEF 敵を処理する、魔法耐性へ対応する、debuff 中の敵を狙って効率化する、といった複数クラスの差分を同じダメージ式上で表現できる。

## 範囲・ターゲット形状

ターゲット形状は、選ばれた anchor から「どのように対象へ効果を配るか」を決める仕組みである。これは単なる範囲攻撃一覧ではなく、攻撃・回復・buff / debuff・dispel などが共有する対象解決システムである。

| 形状      | 内容                                                           | 状態     |
| --------- | -------------------------------------------------------------- | -------- |
| single    | 攻撃可能プールから 1 体を選ぶ。複数 Hit なら同一対象へ繰り返す | 実装済み |
| aoe       | anchor と半径内の対象へ適用する                                | 実装済み |
| pierce    | selfOrigin 起点の前方セグメントへ手前から奥へ命中する          | 実装済み |
| chain     | anchor から同陣営内を距離条件で連鎖する                        | 実装済み |
| multiLock | 並べた対象プールへ Hit をラウンドロビン配分する                | 実装済み |
| scatter   | anchor 周辺へ着弾を分散し、命中判定半径で解決する              | 実装済み |

chain と multiLock は、単なる演出ではなくターゲット形状システムとして扱われる。chain は対象間の距離関係と hop を使って命中列を作り、multiLock はターゲット順と hitCount によって複数対象へ Hit を割り当てる。

このため、対象選択、Hit 数、適用タイミング、VFX 再生は一体で設計される。`chainDurationSec` や `hitDurationSec` は見た目だけでなく、Hit 適用の時間分散にも関係する。

## メカニクスとクラス個性の関係

| 操作点                         | 個性付けの方向                                                  |
| ------------------------------ | --------------------------------------------------------------- |
| ターゲット選択                 | 高 DEF、瀕死、遠隔、高 HP など、処理対象の違いを作る            |
| Hit / Attack / Gauge           | 連撃、攻撃回数、コンボ加速、チャージ回転の違いを作る            |
| 通常攻撃変形                   | 通常攻撃を一時的に別リソース・別効果へ変換する                  |
| 範囲・形状                     | 単体、範囲、射線、連鎖、分散など、火力の当て方を変える          |
| Barrier / 軽減 / Counter       | Survival を単なる HP 回復ではなく、猶予・受け口・反撃へ分解する |
| DoT / Stun / Dispel            | 時間密度、行動可否、状態異常対策を扱う                          |
| DEF / REG / damageTaken / 特効 | 敵の耐性軸や状態条件に応じた適合性を作る                        |

現在の設計では、クラス差分は「同じ効果の数値違い」ではなく、これらの操作点の組み合わせで作られている。たとえば物理 Kill は処理対象と Hit 構造、Flow は位置・時間・形状、Survival はバリア・軽減・解除・反撃によって差分化される。
