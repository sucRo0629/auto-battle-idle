# itch.io — ストアページ・Devlog 方針

**Release M1（体験版）** 公開前後の itch.io 運用メモ。配信チャネル全体の正本は [phase-roadmap.md §Release マイルストーン](./phase-roadmap.md#release-マイルストーン)（**itch.io = 第一配信先**、Devlog / 外宣伝の受け皿）。

**最終更新:** 2026-06

---

## 結論

- **体験版（M1）の数週間〜1〜2 か月前**から、itch.io に **プロジェクトページ + 短い Devlog を数本** 書いておくのを推奨する。
- **今すぐ毎週書く必要はない。** 4d / 6d で見せられる画面ができてから始める方がコスパが高い。
- **中身のない「開発中です」連投は避ける。** 実装 polish と Devlog はトレードオフになる。

---

## Devlog を体験版前に始める理由

| 観点 | 内容 |
| ---- | ---- |
| **フォロワー通知** | itch.io は Devlog 更新とリリースの両方でフォロワーに通知される。公開日に初めてページを作るより、既にフォローされている状態の方が初動を取りやすい。 |
| **ジャンル説明** | 「編成解法型オートバトル RPG」はスクリーンショット 1 枚より **意図の説明** が効く。体験版前の Devlog で「編成が問題そのもの」「オートバトルは検証手段」と伝えておくと、M1 のフィードバックの質も上がる。 |
| **M1 → M2 導線** | M1 は Chapter 1 前半・8 クラスで終わり、初版へ誘導する設計。Devlog で開発意図・ロードマップを共有しておくと、M2 以降の期待値管理に使える。 |
| **zip 前から準備可** | ダウンロード不可の **Draft / 非公開ページ** でも Devlog は書ける。Phase 7（zip）完成前からページと文案を整えられる。 |

---

## 今すぐ書かなくていい理由

- まだ Phase 6（体験版ステージ・画面導線）の途中で、M1 用コンテンツが揃っていない。
- 「開発中です」だけの更新はフォローにも刺さりにくい。
- Devlog は実装時間と競合する。M1 直前の polish を優先する。

---

## 推奨タイミング（本プロジェクト）

| 時期 | やること |
| ---- | -------- |
| **今（Phase 4）** | Devlog は **必須ではない**。M1 で使う **1 行フック・英語キャッチコピー** をメモ程度で固める。 |
| **4d 仕上げ〜6d 導線が見える頃** | itch ページ作成（Draft 可）。**Devlog #1**: ゲームの核（編成が解法）+ 編成 UI / 戦闘の GIF 1〜2 枚。 |
| **M1 の 2〜4 週間前** | **Devlog #2**: 体験版の範囲（8 クラス・Chapter 1 前半・Lv1 キャップ）。**#3**: 体験版で遊べること・フィードバック募集。 |
| **zip 完成（Phase 7）** | 体験版公開。Devlog で「Out now」と合わせて出す。 |

**本数の目安:** 公開前に **2〜4 本、各 300〜800 語（英語）** あれば十分。週刊の長期連載は必須ではない。

---

## 最初の Devlog に入れる内容

体験版前の 1 本目は、次の 3 点が揃っていると効果が高い。

1. **何が楽しいか** — 「編成を組むことがステージ攻略そのもの」（[design-philosophy.md](../design-philosophy.md) の言葉でよい）
2. **他作との違い** — オートバトルは結果確認用、解法探索が主役、など
3. **見えるもの** — `SkillMenuPanel` や戦闘画面の **GIF / スクリーンショット**（英語 UI は **4e（M1 直前）** 後だと M1 と一致する）

## 運用の割り切り

ソロ開発で M1 まで実装が詰まっている場合、Devlog は **「マーケ専用作業」ではなく、M1 の説明資料を先に書く作業」** と割り切る。公開ページの英語文案・Devlog 下書きは itch 上または別メモで管理し、ゲーム spec（`docs/spec/`）には載せない。
